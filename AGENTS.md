# Правила работы агентов - noplagiat-analytics

Этот проект почти полностью создаётся ИИ-агентами (оркестратор плюс субагенты) при минимальном участии человека в ревью. Данные правила существуют для того, чтобы автономная работа оставалась корректной, соответствующей требованиям и пригодной к слиянию. Прочитайте [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md), прежде чем писать код; [docs/TZ.md](docs/TZ.md) - нормативная спецификация (на русском языке). Заметки по инструментарию находятся в [CLAUDE.md](CLAUDE.md) (Vite+ / `vp`).

---

## 1. Инварианты, не подлежащие обсуждению

Это свойства комплаенса и безопасности. Они обеспечиваются типами и тестами; никогда не ослабляйте ни то, ни другое. Если задача, судя по всему, требует нарушить один из них - остановитесь и эскалируйте вопрос человеку.

1. **Никаких ПДн, никогда.** Ни одна колонка, поле структуры, строка лога, фикстура, имя теста или экспорт не могут содержать имя человека, идентификатор автора или текст документа. Единственный идентификатор - непрозрачный `source_check_id`.
2. **k-анонимность реализована на сервере и типизирована.** Публичные DTO строятся только из `compliance::Screened<T>`. Никогда не собирайте публичный ответ из сырых агрегатов, никогда не переносите подавление на фронтенд, никогда не отключайте его в тестах частным случаем через завышенные пороги.
3. **Область видимости RBAC - обязательный параметр запроса.** Каждая функция запроса внутреннего контура принимает `Scope`; фильтрация выполняется в SQL. Никогда не добавляйте внутренний запрос, допускающий «отсутствие области видимости», и никогда не фильтруйте по области видимости в Rust уже после выборки.
4. **Журнал аудита - только на добавление (append-only).** Никаких путей UPDATE/DELETE, никаких изменений схемы, которые их допускают, никаких заданий «очистки» со сроком хранения менее 1 года.
5. **Контракты генерируются, а не редактируются.** `contracts/openapi.json` формируется из Rust (`export-openapi`); `app/src/api/` формируется из контракта (`vp run gen:api`). Ручное редактирование любого из них запрещено - меняйте типы Rust и перегенерируйте.
6. **Миграции только добавляются и в первую очередь аддитивны.** Никогда не изменяйте закоммиченную миграцию; напишите новую. Разрушающие шаги (drop/rename) - только как завершающая фаза цикла expand→migrate→contract, отдельным изменением.
7. **Гейты CI (gates) нельзя обходить.** Никаких `#[ignore]`, никаких `skip`, никаких ослабленных проверок, никакого `-A warnings`, никакого удаления падающего теста ради зелёного статуса. Исправьте код или эскалируйте.

## 2. Критерий готовности (Definition of Done) - для каждого изменения

Изменение считается готовым, только когда локально проходит всё перечисленное ниже:

```bash
cargo fmt --check --manifest-path server/Cargo.toml
```

```bash
cargo clippy --workspace --all-targets --manifest-path server/Cargo.toml -- -D warnings
```

```bash
cargo test --workspace --manifest-path server/Cargo.toml
```

```bash
vp check
```

```bash
vp test
```

```bash
vp run gen:api:check
```

`gen:api:check` перегенерирует клиент из **закоммиченного** контракта во временный каталог и сравнивает результат - он никогда не трогает дерево и не требует cargo. Половина проверки «Rust против контракта» - отдельный гейт, `cargo run --manifest-path server/Cargo.toml --bin export-openapi -- --check contracts/openapi.json`, и это первое задание в CI.

Кроме того, если изменение затрагивает маршруты/DTO: перегенерируйте контракт и клиент (`vp run gen:api`) и закоммитьте их вместе с изменением на Rust (одним атомарным коммитом - дерево никогда не должно содержать устаревший контракт). Если затрагивается SQL: выполните `cargo sqlx prepare` и закоммитьте `.sqlx/`. Если затрагиваются пользовательские сценарии интерфейса или RBAC: выполните `vp run e2e`. Если поведение установки, рантайма или менеджера пакетов выглядит неправильно, выполните `vp env doctor` и приложите его вывод при эскалации.

Сообщайте результаты честно: вставляйте вывод падения, а не пересказывайте его так, чтобы проблема исчезла. Пропущенный шаг обозначается как пропущенный.

## 3. Рабочий процесс

1. **Сориентируйтесь.** Прочитайте соответствующий раздел ARCHITECTURE.md и код, который будете менять. Проверьте `docs/adr/` на предмет действующих решений - не пересматривайте их заново; если решение нужно заменить, напишите новый ADR.
2. **Планируйте мелко.** Один вертикальный срез (slice) на изменение: миграция (если нужна) → тип домена → запрос → обработчик → перегенерация контракта → перегенерация клиента → интерфейс → тесты. Предпочитайте несколько небольших слияний одному широкому.
3. **Пишите тест вместе с функциональностью.** Новая конечная точка → строки матрицы RBAC + покрытие контрактом. Новый агрегат → сравнение полным перебором (brute force) с фикстурами. Новое публичное поле → покрытие property-тестами подавления. Функциональность без своего гейта не считается готовой.
4. **Проверяйте как скептик.** Выполните критерий готовности. Для визуальной работы запустите приложение на фикстурах и сверьте фактически отрисованные числа с `fixtures/expected.json` - не полагайтесь на «оно компилируется».
5. **Фиксируйте.** Новая зависимость, таблица, группа конечных точек или архитектурное отклонение → ADR в том же изменении. Обновите ARCHITECTURE.md, если карта больше не соответствует местности.

### Коммиты и ветки

- Ветвитесь от `main`; Conventional Commits (`feat(api): …`, `fix(compliance): …`, `chore(deps): …`). Одно логическое изменение на коммит; сгенерированные файлы коммитятся вместе с изменением их источника.
- Никогда не коммитьте секреты, файлы `.env` или реальные продуктивные выгрузки. Фикстуры - единственные данные, разрешённые в репозитории.

## 4. Параллельная работа - границы владения

Субагенты, работающие одновременно, должны оставаться в пределах одной дорожки (lane); правки, пересекающие дорожки, требуют упорядочивания оркестратором.

| Дорожка               | Владеет                                             | Поверхность соприкосновения                                                  |
| --------------------- | --------------------------------------------------- | ---------------------------------------------------------------------------- |
| `domain`/`compliance` | бизнес-правила, подавление, типы областей видимости | типы, потребляемые всеми остальными дорожками - меняйте первыми и в одиночку |
| `db` + `migrations`   | схема, запросы, агрегаты, `.sqlx/`                  | сигнатуры запросов                                                           |
| `ingest`              | клиент исходной системы, CSV, планировщик, пакеты   | `NewCheck`, справочники                                                      |
| `reports`             | PDF/XLSX, снимки, шаблоны                           | DTO, прошедшие подавление                                                    |
| `api`                 | маршрутизатор, слои, экстракторы, OpenAPI           | `contracts/openapi.json`                                                     |
| `app` (фронтенд)      | маршруты, компоненты, i18n, стили                   | только сгенерированный `src/api/`                                            |
| `fixtures`/`e2e`      | генератор, ожидаемые значения, Playwright           | всё, только на чтение                                                        |

Правила взаимодействия: файл контракта - точка синхронизации между дорожками бэкенда и фронтенда: сначала вливается бэкенд, затем фронтенд перегенерирует клиент. Общие файлы (`tokens.css`, `i18n/*`, `queries.ts`) в пределах одной волны задач имеют единственного писателя. Миграции строго сериализованы: «следующий номер миграции» в каждый момент времени удерживает только один агент.

## 5. Соглашения по коду

**Rust**

- Ошибки: перечисления `thiserror` для каждого крейта; `ApiError`/problem+json на границе. `unwrap`/`expect` запрещены clippy в `api`, `db`, `compliance` - обрабатывайте или пробрасывайте.
- Весь SQL - через макросы `sqlx::query!`/`query_as!` (проверяются на этапе компиляции). Динамический SQL - только через проверенный построитель фильтров в `db::filters`; никогда не склеивайте пользовательский ввод в строку.
- Публичный API каждого крейта продуман: по умолчанию `pub(crate)`; небольшая документированная `pub`-поверхность.
- Никаких новых зависимостей без обосновывающей их строки в ADR; предпочитайте std/tokio/уже присутствующие крейты.

**TypeScript**

- `strict` везде; никакого `any`, никакого оператора не-null `!` вне тестов, никакого `@ts-ignore` (если это действительно необходимо, используйте `@ts-expect-error` с указанием причины).
- Все серверные данные поступают через сгенерированный клиент; все параметры поиска маршрутов - через общую схему Zod. Никаких произвольных `fetch`.
- Цвета - только из переменных `tokens.css`; строки, видимые пользователю, - только из сообщений paraglide (`apps/web/messages/*.json` - все три локали в одном коммите; тест паритета в `src/lib/i18n.test.ts` требует идентичных ключей и подстановок, а вы предоставляете реальный текст на KK/RU, а не англоязычные заглушки). Никогда не импортируйте внутренности `src/paraglide/`, кроме `messages.js` и `runtime.js`; никогда не редактируйте `src/paraglide/` вручную.
- Компоненты принимают сгенерированные типы API в качестве пропсов; графики отрисовываются через обёртки в `components/charts/`, а не напрямую через `@tanstack/charts` в маршрутах.

**Комментарии** формулируют ограничения, которые не выразить кодом (`// complementary suppression: see ADR-002 / TZ §6.2`), а не пересказывают диф.

## 6. Проверочные данные

- `fixtures/` детерминирован (ГПСЧ с фиксированным зерном). Если вы меняете генератор, перегенерируйте `expected.json` скриптом полного перебора в том же коммите и укажите это в теле коммита.
- Набор фикстур намеренно содержит группы размером 1..k+1. Если ваша функциональность затрагивает агрегацию или отображение, глазами проверьте хотя бы одну подавленную ячейку в запущенном приложении (`vp dev` + БД, засеянная через `vp run seed`).
- Никогда не «чините» падающий тест ожидаемых значений, подгоняя `expected.json` под приложение; пересчитайте его скриптом полного перебора и разберитесь в любом расхождении.

## 7. Когда остановиться и спросить человека

- Всё, что затрагивает список инвариантов §1 в сторону ослабления.
- Учётные данные, регистрация SSO-клиента, продуктивные URL, выгрузки реальных данных из `noplagiat.tou.edu.kz`.
- Удаление данных, удаление колонок/таблиц, изменение срока хранения аудита.
- Публикация чего-либо на портале или во внешних сервисах.
- Неоднозначность между TZ.md и ARCHITECTURE.md - обозначьте конфликт со ссылками на оба документа; TZ.md имеет приоритет в вопросе _что_, ARCHITECTURE.md - в вопросе _как_.

Всё остальное: действуйте автономно, проверяйтесь гейтами и оставляйте дерево зелёным.
