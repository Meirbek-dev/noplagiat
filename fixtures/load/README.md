Проверяемый бюджет - **D9** (docs/PLAN.md) и пункт 5 из ARCHITECTURE.md §7:
`/api/public/summary` **p95 < 300 ms** при засеянном хранилище в **250 000 строк**, что
соответствует формулировке TZ §7 «рост объёма данных минимум в 5 раз (до 250 000+ записей)».

## 1. Засев хранилища масштаба load

> **Это заменяет вашу базу данных для разработки.** `--reset` удаляет схему `public` и
> заново применяет миграции. Раздел 4 восстанавливает малый набор фикстур; сделайте это
> сразу после завершения измерения, потому что все остальные тесты в репозитории ожидают
> малый масштаб - `fixtures/expected.json` перегенерируется под каждый масштаб, и
> `cargo test` сравнивает именно с ним.

```bash
bun fixtures/generate.ts --scale load
bun fixtures/expected.ts
bun fixtures/seed.ts --reset
```

`seed.ts` ничего не перегенерирует, если `fixtures/out/manifest.json` уже существует,
поэтому масштаб на деле переключает именно явный `generate.ts --scale load` выше; передача
`--scale load --force --reset` одному только `seed.ts` делает то же самое одной командой.

Засев запускает **настоящий** импортёр CSV (`cargo run --bin ingest-csv`) по одному разу на
учебный год, поэтому он заодно прогоняет и конвейер, обезличивающий данные (ADR-008 §10).
На масштабе load рассчитывайте на несколько минут.

Затем убедитесь в состоянии хранилища:

```bash
psql "$APP_DATABASE_URL" -c 'SELECT count(*) FROM checks'
psql "$APP_DATABASE_URL" -c 'SELECT max(finished_at) FROM ingest_batches'
```

### Длительность обновления материализованных представлений (PLAN.md R6)

Показатель, который PLAN.md требует зафиксировать рядом с бюджетом запроса.
`refresh_aggregates()` - это то, что импортёр вызывает в конце каждой партии:

```bash
psql "$APP_DATABASE_URL" -c '\timing on' -c 'SELECT refresh_aggregates()'
```

Импортёр логирует ту же длительность по каждой партии; любой из источников является
приемлемым свидетельством.

## 2. Запуск сервера

Сборка **release**. Debug-сборка измеряет `-O0` компилятора rustc, а не архитектуру:

```bash
APP_LISTEN_ADDR=127.0.0.1:8085 RUST_LOG=warn \
  cargo run --release --manifest-path server/Cargo.toml --bin noplagiat-server
```

- `APP_LISTEN_ADDR=127.0.0.1:8085` - отдельный порт, чтобы параллельный стек `vp dev` на
  8080 остался нетронутым.
- `RUST_LOG=warn` - логирование каждого запроса не бесплатно при 50 VU.
- Публичному контуру сессия не нужна, поэтому настройка аутентификации не требуется.

Оба прогонщика сначала опрашивают `/readyz` и отказываются работать против не поднятого
сервера.

## 3. Запуск нагрузочного теста

```bash
BASE=http://127.0.0.1:8085 k6 run fixtures/load/summary.js
```

k6 завершается с кодом **99**, когда порог превышен, и именно это заставляет ночной
workflow падать, а не просто сообщать. `k6-summary.json` пишется в рабочий каталог и
выгружается как артефакт CI.

Проверить скрипт, не запуская его:

```bash
k6 inspect fixtures/load/summary.js
```

### Без k6

`bench.ts` требует только bun и покрывает те же два эндпоинта и те же наборы фильтров.
Это более грубый инструмент - последовательный и с фиксированной конкурентностью вместо
нарастающих VU, - поэтому он является свидетельством, а не шлюзом:

```bash
BASE=http://127.0.0.1:8085 bun fixtures/load/bench.ts
```

## 4. Восстановление малого набора фикстур

Сделайте это сразу после измерения. Всё остальное в репозитории - `cargo test`,
`vp test`, `vp run e2e`, `fixtures/expected.json` - написано под малый масштаб:

```bash
bun fixtures/generate.ts --scale small
bun fixtures/expected.ts
bun fixtures/seed.ts --reset
```

## Что измеряют сценарии

`summary.js` запускает два сценария, потому что из-за кэширования они измеряют разные вещи.

- **`summary`** - `GET /api/public/summary` без строки запроса. Публичные ответы несут
  `Cache-Control: public, max-age=3600` и ETag (ARCHITECTURE.md §7, пункт 2), поэтому это
  первая отрисовка дашборда на прогретом пути. На нём висит порог D9,
  `http_req_duration{scenario:summary} p(95)<300`.
- **`filters`** - `timeseries` и `histogram` со случайными комбинациями `period` /
  `faculty` / `work_type` / `status`. Каждый запрос является отдельным ключом кэша,
  поэтому чтение агрегата действительно выполняется на каждом из них. Это проба
  масштабируемости; её бюджет намеренно свободнее (`p(95)<1000`), потому что это не первая
  отрисовка, видимая пользователю.

Коды словарей в обоих скриптах берутся из `fixtures/dictionaries.sql`.
`crates/api/src/query.rs` отвечает `422` на неизвестный код, поэтому устаревший список
проявляется как доля неуспешных проверок, а не как втихую оптимистичные тайминги.

## Ограничитель частоты запросов и почему оба прогонщика выставляют `X-Forwarded-For`

Публичный контур ограничен **600 запросами в минуту с одного адреса** при всплеске до 120
(`RateLimitConfig::default`, ADR-012 §5). Ключом служит первый хоп `X-Forwarded-For` от
шлюза с откатом на peer сокета.

Поэтому нагрузочный тест с одного хоста - это один адрес. Без заголовка прогон на 70 VU
получает **429 на 99.97 % запросов примерно за миллисекунду** и сообщает p95, описывающий
ограничитель, а не хранилище: это не гипотеза, а то, что измерил первый прогон 30.08.2026.

Поэтому и `summary.js`, и `bench.ts` проставляют отдельный синтетический адрес на каждый
запрос. Это моделирует развёртывание, а не обходит ограничитель: в продакшене nginx
терминирует множество разных посетителей и выставляет этот заголовок для каждого, поэтому
N запросов в секунду с N адресов - _достоверная_ модель, а N запросов в секунду с одного
адреса - нет. Сам ограничитель покрыт модульными тестами в `crates/api`.

Если вы видите почти полную долю отказов при таймингах около 1 ms - причина именно в этом.
