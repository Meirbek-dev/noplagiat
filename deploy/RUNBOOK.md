# Операционное руководство (runbook) - noplagiat-analytics

## Топология

Стек Compose поднимает четыре сервиса:

- `gateway`: единственная точка входа HTTP, публикуется на `GATEWAY_PORT` (8080 по умолчанию).
- `web`: Node.js исполняет SSR-бандл TanStack Start и отдаёт собранные клиентские ассеты.
- `server`: Rust/Axum обслуживает `/api/*`, `/healthz` и `/readyz`.
- `postgres`: PostgreSQL 18 в приватной сети `data`.

nginx направляет `/api`, `/api/*`, `/healthz` и `/readyz` в Rust и **резервирует**
`/metrics`, отвечая на него самостоятельно кодом `444`, - этот путь никогда не
проксируется на публичном слушателе (см. «Мониторинг»). Все остальные запросы
уходят в Node-сервис SSR. Порты Rust и Node открыты только внутри сети Compose;
на хосте они не публикуются.

nginx также владеет заголовками безопасности документа. Процесс SSR не выставляет
ни одного собственного, поэтому `frame-ancestors`, `X-Frame-Options`, `nosniff` и
`Referrer-Policy` для каждого HTML-ответа задаются в `deploy/nginx.conf`: `'none'`
везде, кроме `/embed`, который прибит к origin-ам портала. Поэтому правка этого
файла - изменение в безопасности, а не в маршрутизации. Rust API выставляет
собственные заголовки для `/api/*`, и nginx намеренно не добавляет там второй
комплект.

`deploy/nginx.conf` монтируется не в `conf.d`, а в `/etc/nginx/templates/default.conf.template`:
entrypoint образа подставляет в него адрес DNS рантайма перед стартом мастер-процесса.
Файл поэтому проходит через `envsubst`, и `${...}` в нём - подстановка на старте
контейнера, а не текст конфигурации; подробности и причина - в разделе
«Podman вместо Docker».

## Запуск полного локального стека

Создайте игнорируемый файл окружения и замените в нём плейсхолдеры пароля одним и
тем же URL-безопасным локальным секретом в `POSTGRES_PASSWORD` и
`APP_DATABASE_URL`:

```bash
cp deploy/env.example deploy/.env
```

Аутентификацию настраивать не нужно: вход выполняется по логину и паролю из
таблицы `users` (ADR-017). На свежем стенде учётных записей нет, поэтому сервер
запускается, пишет предупреждение и не пускает никого - пока администратор не
создаст первую запись (см. «Первый администратор» ниже).

Отрисуйте конфигурацию перед запуском:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml config
```

Соберите и запустите все сервисы:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml up --build -d
```

Приложение доступно по адресу `http://localhost:8080`. Полезные проверки:

```bash
curl --fail http://localhost:8080/healthz
curl --fail http://localhost:8080/readyz
curl --fail http://localhost:8080/
```

Просмотр состояния сервисов и логов:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml ps
docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs -f gateway web server postgres
```

### Podman вместо Docker

Стек собран и проверен под rootless podman в WSL2 (PLAN.md срез 4). Все команды
выше работают как `podman compose ...`, но podman - не полная замена: четыре
отличия проявляются как отказы, которые не выглядят связанными с рантаймом.

**`podman compose` собирает классическим сборщиком, а не BuildKit.** podman
делегирует исполнение установленному `docker-compose`, а тот, не найдя за
API-сокетом BuildKit, откатывается к классическому сборщику - он помечает
собранные образы меткой `com.docker.compose.image.builder=classic`. У классического
сборщика **нет** соглашения `<dockerfile>.dockerignore`: он читает корневой
`.dockerignore` и только его. Поэтому корневой `.dockerignore` перечисляет пути
обоих образов и обязан оставаться надмножеством `deploy/Dockerfile.web.dockerignore`,
который под BuildKit сужает контекст web дополнительно. Путь, забытый в корневом
файле, под Docker не ломает ничего, а под podman роняет сборку на `COPY`:

```
building at STEP "COPY package.json bun.lock ./": copier: stat: "/package.json": no such file or directory
```

**Адрес DNS у podman другой.** Docker всегда отвечает на встроенном
`127.0.0.11`; podman поднимает aardvark-dns на адресе шлюза той подсети, которую
выделил сети (`10.89.x.1`). Записанный в конфигурацию жёстко, любой из двух
адресов делает апстримы неразрешимыми на другом рантайме, и nginx отвечает
`502 no live upstreams` на **каждый** маршрут, включая `/healthz`, - при том что
`server` и `web` рапортуют `healthy`. Поэтому `deploy/nginx.conf` монтируется в
`/etc/nginx/templates/default.conf.template`, а не прямо в `conf.d`: штатный
entrypoint образа (`15-local-resolvers.envsh`, включается переменной
`NGINX_ENTRYPOINT_LOCAL_RESOLVERS`) подставляет `${NGINX_LOCAL_RESOLVERS}` из
`/etc/resolv.conf` контейнера. Сам nginx прочитать `/etc/resolv.conf` не умеет:
`resolver local=on` - директива NGINX Plus, открытый 1.31 разбирает `local=on`
как имя хоста и отказывается стартовать. Проверить подстановку:

```bash
MSYS_NO_PATHCONV=1 podman exec deploy-gateway-1 \
  grep '^resolver' /etc/nginx/conf.d/default.conf
```

**Виртуальной машине WSL нужны явные лимиты памяти.** Релизная сборка Rust -
самый тяжёлый шаг во всём стеке. Без `memory=` в `%USERPROFILE%\.wslconfig` WSL2
берёт за потолок половину ОЗУ хоста и растёт до него; Windows фиксирует нехватку
виртуальной памяти (журнал «Система», `Resource-Exhaustion-Detector`, код 2004) и
через несколько минут снимает служебную ВМ. Compose в этот момент читает поток
сборки из исчезнувшего сокета и сообщает единственную строку, ничего не говорящую
о причине:

```
[+] up 0/1
 - Image deploy-server Building   376.4s
unexpected EOF
```

Признак того, что это именно оно, а не ошибка сборки: `podman machine inspect`
показывает `"State": "stopped"`, а уже собранные слои образа на месте. Рабочие
значения для хоста с 32 ГБ ОЗУ - при них сборка держится около 3,5 ГБ:

```ini
[wsl2]
memory=10GB
swap=8GB
processors=8
```

Файл читается парсером INI и **обязан** иметь переводы строк CRLF или LF. Файл с
одними CR разбирается как одна строка, и не применяется ни один параметр - молча,
без диагностики. Проверяйте `od -c "$USERPROFILE/.wslconfig" | head`, а не глазами.
Изменения вступают в силу после `wsl --shutdown`.

**Git Bash на Windows подменяет пути в аргументах.** MSYS переписывает всё, что
похоже на абсолютный путь Unix, в путь Windows **до** того, как аргумент дойдёт до
контейнера, поэтому `--dir /tmp/stats` приезжает как `C:/Users/.../Temp/stats` и
шаг падает с `No such file or directory` на пути, которого вы не писали. Для любой
команды `podman exec` с абсолютным путём внутри контейнера:

```bash
MSYS_NO_PATHCONV=1 podman exec deploy-server-1 ingest-csv --dir /tmp/stats --source csv-backfill
```

В PowerShell и в WSL-оболочке подмены нет; отличие касается только Git Bash.

**Держите тег базового образа Rust равным `server/rust-toolchain.toml`.**
`deploy/Dockerfile.server` работает из `/build`, а rustup ищет `rust-toolchain.toml`
только вверх по дереву - файл лежит в `/build/server/` и найден не будет. Значит
образ собирается тем компилятором, который стоит в базовом образе, и расхождение
тега с закреплённым каналом даёт релизный образ, собранный **не тем** компилятором,
которым проверяет CI, - без единого предупреждения.

Миграции применяются автоматически при старте `server` (`sqlx migrate` по
`server/migrations/*.sql`). Каждая выполняется в собственной транзакции и под
консультативной блокировкой Postgres, поэтому одновременный старт нескольких
реплик безопасен, а неудавшаяся миграция не оставляет наполовину применённой
схемы.

Сбой миграции завершает процесс - но `restart: unless-stopped` означает, что
контейнер перезапускается немедленно и бесконечно, поэтому выбирать момент, когда
посмотреть, вам не дадут. Сначала остановите его, затем читайте логи:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml stop server
docker compose --env-file deploy/.env -f deploy/docker-compose.yml logs server | tail -50
```

Два режима отказа, которые нужно уметь распознавать:

- **Миграции применяются только вперёд.** Обратных миграций нет, поэтому после
  того как миграция применена, откат на предыдущий образ не поддерживается.
  Плохая миграция лечится накатом _вперёд_ - корректирующей миграцией - или
  восстановлением из резервной копии; планируйте релизы соответственно.
- **Никогда не редактируйте уже применённую миграцию.** `sqlx` хранит
  контрольную сумму по каждому файлу; её изменение приводит к тому, что все
  последующие запуски падают с рассогласованием версий, которое совершенно не
  похоже на вызвавшую его правку.

`/readyz` проверяет доступность базы данных **и** свежесть импорта: он отвечает `503` с
`status: "ingest_stale"`, когда самая новая _успешная_ партия старше
`APP_INGEST_MAX_AGE_SECONDS` (26 ч по умолчанию). Хранилище, которое никогда не наполняли,
считается готовым, а не устаревшим, - это свежая установка (ADR-014 §9).

Проверка здоровья контейнера `server` - это `/readyz`, поэтому `docker compose ps`
показывает `unhealthy`, когда данные устаревают. **Шлюз намеренно не ждёт этого
состояния здоровья** (`condition: service_started`): устаревшие данные не должны
выводить из строя публичный дашборд и собственные пробы живости портала.

**Зарегистрируйте хотя бы один источник импорта, прежде чем полагаться на всё
это.** `ingest_sources` поставляется пустой, и ни одна миграция его не заполняет,
поэтому развёртывание, поднятое по одному этому документу, не имеет ни одного
включённого источника: ночной тик отрабатывает каждую ночь и ничего не делает.
Это состояние читается как «готово» (никогда не наполнявшееся не считается
устаревшим), но в тот момент, когда разовый CSV-бэкфилл запишет партию со
статусом `succeeded`, `/readyz` ровно через 26 ч перейдёт в `503` и сам никогда из
него не выйдет. Создайте источник через `POST /api/admin/ingest/sources` и
убедитесь, что ночная партия отрабатывает.

**Когда `/readyz` сообщает `ingest_stale`:** не отработал один ночной импорт; сам
дашборд обслуживается корректно. Тайминг детерминирован - тик в 02:00 +05:00,
бюджет 26 ч, поэтому одна пропущенная ночь переводит `/readyz` в `503` в
**04:00 +05:00 следующего дня**, и он остаётся в `503` примерно 22 ч до
следующего успешного тика. Изучите `GET /api/admin/ingest/batches`, затем
перезапустите импорт через `POST /api/admin/ingest/run`.

Сообщите тем, кто потребляет эти эндпоинты, что **`503` со
`"status":"ingest_stale"` - это оповещение о свежести данных, а не о
доступности.** Сегодня ничто в этом репозитории по нему не алертит: нет ни
конфигурации Prometheus, ни правила алерта, а `restart: unless-stopped` не
реагирует на состояние проверки здоровья, поэтому незамеченная пропущенная ночь
сейчас невидима, пока кто-нибудь не посмотрит на дашборд. Если портал делает
проверку здоровья `/readyz` и снимает origin с ротации при отказе, он положит
сайт из-за устаревших данных - ровно того исхода, ради предотвращения которого у
шлюза выбран `service_started`. Направляйте внешние проверки ротации на
`/healthz`.

`/metrics` реализован (текстовый формат Prometheus, ADR-014 §8), но на внешнем origin шлюз
отвечает на него `444` - см. «Мониторинг» ниже.

Остановить стек без удаления данных базы:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml down
```

Не передавайте `--volumes`, если только вы намеренно не удаляете локальный том
базы данных.

Прежний каркас использовал PostgreSQL 19 beta. Каталоги данных PostgreSQL не
обратносовместимы: не подключайте том, инициализированный тем образом, к
PostgreSQL 18. Выгрузите данные исходным образом, проверьте резервную копию и
восстановите её в новый том PostgreSQL 18. Никогда не удаляйте старый том до
того, как восстановление проверено.

**Рассогласование версий здесь не заявляет о себе - оно выглядит как пустая база
данных.** Начиная с PostgreSQL 18 официальный образ размещает кластер в
подкаталоге с версией (`PGDATA=/var/lib/postgresql/18/docker`), объявляя при этом
свой том уровнем выше, в `/var/lib/postgresql`, - именно поэтому
`docker-compose.yml` монтирует `pgdata` в родительский каталог; это монтирование
корректно, не «чините» его. Следствие в том, что подключение тома, записанного
любым образом до 17 включительно (где кластер лежал непосредственно в корне),
даёт контейнеру 18 пустой `18/docker`, поэтому он выполняет `initdb` и стартует
**совершенно новый пустой кластер рядом с нетронутыми старыми файлами**. Никакой
ошибки не возникает; приложение просто поднимается без данных. Проверяйте явно
после любого переноса тома, прежде чем считать работу выполненной:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T postgres \
  sh -c 'ls -la /var/lib/postgresql && psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT version()" \
         && psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c "SELECT count(*) FROM checks"'
```

Учтите также, что Compose выводит имена томов из имени проекта, которым является
каталог compose-файла: `docker volume ls` показывает **`deploy_pgdata`** и
**`deploy_reports`**, а не `pgdata` и `reports`.

### Наполнение свежего стека данными

`up -d` на чистой машине создаёт **новый пустой том** `deploy_pgdata`. Миграции
отработают, `settings` засеется, `/readyz` ответит `200` - и дашборд при этом
покажет «недостаточно данных» в каждой панели. Это не отказ: хранилище, которое
никогда не наполняли, считается готовым (ADR-014 §9), а подавление по
k-анонимности на пустом множестве обязано выводить именно это. Убедиться, что
дело в отсутствии данных, а не в маршрутизации:

```bash
podman compose -f deploy/docker-compose.yml exec -T postgres \
  psql -U noplagiat -d noplagiat -tAc \
  "select 'checks='||(select count(*) from checks)||' batches='||(select count(*) from ingest_batches)"
```

`faculties = 1` на свежем стеке - это тоже норма: миграция `0002` засевает только
сентинелы `UNASSIGNED` и `other` (ADR-008 §6), настоящих справочников репозиторий
не содержит.

Для **синтетических** данных используйте `fixtures/` (см. `fixtures/README.md`);
`seed.ts` ходит в базу по `APP_DATABASE_URL` и рассчитан на нативный PostgreSQL,
а не на контейнер - compose намеренно не публикует порт 5432.

Для **реальных** выгрузок путь тот же, что в разделе про W4.3 ниже, но пеппер
берётся локальный, а не продакшен-овый:

```bash
podman cp stats deploy-server-1:/tmp/stats
MSYS_NO_PATHCONV=1 podman exec deploy-server-1 \
  ingest-csv --dir /tmp/stats --source csv-backfill-local
podman exec -u root deploy-server-1 rm -rf /tmp/stats   # выгрузки содержат ПДн
```

`APP_DATABASE_URL` и `APP_INGEST_PEPPER` уже есть в окружении контейнера, поэтому
задавать их повторно не нужно - и именно поэтому импорт получается тем же
пеппером, что и весь остальной стек. Последняя строка не факультативна: конвейер
обезличивает **на входе**, а копия `stats/` внутри контейнера остаётся сырой,
и `restart: unless-stopped` держит её там до пересоздания контейнера.

Чего ждать после такого импорта: сводка, динамика во времени, распределение
оригинальности и эскалации наполняются настоящими числами, а **разрезы по
факультету и по типу работы вырождаются в одну корзину** - все проверки попадают
на `UNASSIGNED` / `other`. Причина не в импорте: `staff_units` и `work_type_rules`
пусты, а вывести их из `stats/` невозможно - исходные CSV несут только ФИО и
e-mail проверяющего и ни одного поля с подразделением. Чтобы эти два разреза
заработали, нужен внешний источник сопоставления «e-mail → факультет/кафедра»
(HR или AD) и настоящие правила по шаблону названия работы.

сопоставление построены из общедоступной структуры сайта университета

подразделениям) и совмещены с выгрузками по ФИО проверяющего. Инструменты -
`scripts/real-units/{scrape,match,build_sql}.py`; артефакты пишутся в `stats/`
(каталог в `.gitignore`, наружу не уходит):

  (`FAC91`, `DEP99`, ...) на RU/KK/EN плюс типы работ по ТЗ; идемпотентен;
- `stats/real-staff-units.csv` - «e-mail → подразделение» (сырьё с адресами,
  остаётся локальным); в базу уходит только `stats/real-staff-units.sql`
  с HMAC и маскированными метками, пеппер берётся из `deploy/.env`;
- `stats/real-work-type-rules.sql` - расширение правил типов работ под
  реальные названия-имена файлов («дипломная_работа», голые «диплом»,
  «статья», «мақала» и т.п.), приоритеты 70+ - после фраз ADR-008.

Порядок: применить четыре SQL (`real-dictionaries`, затем
`fixtures/work-type-rules.sql` и `fixtures/initiator-rules.sql`, затем
`real-staff-units`, затем `real-work-type-rules`) через
`podman exec -i deploy-postgres-1 psql -U noplagiat -d noplagiat -v ON_ERROR_STOP=1 -q`
и повторить импорт из раздела выше - upsert перепишет атрибуцию на месте.

Результат на выгрузках 2021-2026: сопоставлено 158 из 177 проверяющих
(157 - до кафедры), что атрибутирует ~36,5 % проверок; остаток - в основном
сервисный аккаунт `antiplagiat@tou.edu.kz` (~58 % всех проверок), который
неатрибутируем в принципе. Без него покрытие атрибутируемых проверок ~84 %.
По типам работ классифицируется ~15 % названий; остальное - свободные имена
файлов, честно остающиеся «Иное».

Оговорки: это снимок _текущего_ состава ППС, применённый ко всем годам, -
для прошлых лет атрибуция приблизительна (сноска на дашборде это говорит);
запрос D2 остаётся в силе, официальное сопоставление офиса регистратора
должно заменить скрейп через админ-редактор справочников.

Оставшийся крупный остаток «Не распределено» - осознанный: кроме сервисного
аккаунта это центральные операторы (оператор с адресом `@tou.edu.kz`,
проверяющий дипломные всех кафедр, редакция научных журналов, отдел науки) -
их привязка к одному факультету исказила бы разрезы. После применения
сопоставления годовые отчёты за все пять лет перегенерированы
(`generate-report`, 31.08.2026) - с реальными названиями факультетов и
сноской о сопоставлении.

Чтобы открыть `/app/*`, создайте учётную запись - без неё маршрут отвечает `307`
на `/login`, а войти нечем:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml \
  exec server manage-users create-user --username local-admin --role admin
```

Проверить сеанс можно тем же паролем, что был задан в приглашении:

```bash
curl -sS -c jar.txt -X POST http://localhost:8080/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"local-admin","password":"<пароль>"}'
curl -sS -b jar.txt http://localhost:8080/api/auth/me
```

## Учётные записи и первый администратор (ADR-017)

Как работает вход целиком - [docs/AUTH.md](../docs/AUTH.md). Здесь - только процедуры.

Вход во внутренний контур - это логин и пароль из таблицы `users`. Ни один
HTTP-маршрут не создаёт учётную запись и не задаёт пароль: это делает только CLI
`manage-users`, который поставляется в том же образе, что и сервер. Поэтому
завести администратора может лишь тот, у кого есть доступ к хосту развёртывания
и к базе, - то же лицо, через которое TZ §5 проводит назначение ролей.

Все команды ниже выполняются внутри контейнера `server`; префикс для
compose-стенда:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec server
```

**Первый администратор.** На свежем стенде учётных записей нет, сервер пишет об
этом предупреждение при старте, и войти невозможно, пока не выполнено:

```bash
manage-users create-user --username admin --role admin
```

CLI запросит пароль дважды, не отображая ввод. Минимум - 12 символов; требований
к набору символов нет (NIST SP 800-63B §5.1.1.2: значение имеет длина).

**Пароль никогда не передаётся аргументом.** Флага `--password` нет: аргумент
попал бы в историю оболочки и в вывод `ps`. Для неинтерактивного развёртывания
передайте пароль через `APP_ADMIN_PASSWORD` в окружении самой команды.

**Остальные роли.** Декан и заведующий кафедрой обязаны называть своё
подразделение - грант без подразделения CLI отклоняет, потому что
`RoleGrant::scope` читает его как «данных не видно», и такая запись выглядела бы
выданной, ничего не показывая (ADR-012 §4):

```bash
manage-users create-user --username dean.fac03 --role dean      --faculty FAC03
manage-users create-user --username head.dep11 --role dept_head --department DEP11
manage-users create-user --username ethics.01  --role ethics
```

**Эксплуатация.**

```bash
manage-users list                                   # кто есть и с какими ролями
manage-users set-password --username admin          # сброс пароля
manage-users grant  --username u --role dean --faculty FAC03
manage-users revoke --username u --role dean --faculty FAC03
manage-users deactivate --username u                # закрыть доступ
manage-users activate   --username u
```

`set-password` и `deactivate` завершают все живые сеансы этой учётной записи в
той же транзакции: смена пароля, после которой прежняя cookie ещё работает, -
это не смена пароля.

Роли можно выдавать и отзывать также через админ-раздел (`/admin/roles`,
TZ §4.6); пароль - нет, для него есть только CLI.

## Нативная разработка

Для нативного процесса Rust или фронтенда используйте отдельно управляемый
локальный экземпляр PostgreSQL и команды из `AGENTS.md`. Этот compose-файл
намеренно не публикует порты PostgreSQL, Rust и Node; он моделирует сетевые
границы развёртывания. Оставляйте базовый адрес API фронтенда незаданным, чтобы
при тестировании полного стека запросы оставались same-origin и шли через nginx.

## Развёртывание в продакшене

- Терминируйте TLS на университетском обратном прокси и направляйте один origin на nginx
  `gateway`. Задайте `APP_PUBLIC_BASE_URL` равным именно этому внешнему HTTPS-origin.
- Внедряйте `POSTGRES_PASSWORD` и `APP_DATABASE_URL` из
  хранилища секретов развёртывания. Не копируйте `deploy/env.example` без изменений и не
  помещайте продакшен-учётные данные в закоммиченный файл или в аргумент сборки образа.
- Держите `server`, `web` и `postgres` неопубликованными. Ограничьте публикацию шлюза на
  межсетевом экране хоста или в сети платформы университетским прокси.
- Собирайте неизменяемые теги образов в CI и продвигайте одни и те же образы между
  контурами. Compose-файл фиксирует мажорные линии рантаймов, а не неизменяемые дайджесты
  образов; продакшен-манифест релиза должен фиксировать проверенные дайджесты.
- nginx сохраняет `X-Forwarded-Proto` и `X-Forwarded-Host`, переданные университетским
  прокси, откатываясь для локального использования к непосредственно наблюдаемым значениям
  запроса. Node-адаптер доверяет нормализованным значениям, которые передал nginx. В
  продакшене ограничьте вход на шлюз университетским прокси и не выставляйте Node-контейнер
  наружу напрямую.

## Мониторинг

`/metrics` отдаёт текстовый формат Prometheus на процессе Rust: `http_requests_total`,
`http_request_duration_seconds`, четыре gauge-метрики `ingest_*`, `suppression_screened_cells_total`
и `audit_write_failures_total` (ADR-014 §8).

**С внешнего origin он недоступен.** `deploy/nginx.conf` отвечает `444` - соединение
закрывается без ответа - на публичном слушателе. Путь остаётся объявленным, чтобы его не
могло занять что-то другое (ARCHITECTURE.md §8).

Чтобы позволить системе мониторинга снимать метрики, раскомментируйте второй блок `server`
внизу `nginx.conf`, замените `10.0.0.0/8` на **фактический** CIDR сети мониторинга и
опубликуйте порт 9090 только в сети мониторинга - никогда в `ports:`
`docker-compose.yml`, который отображается на хост. Зафиксируйте это изменение здесь,
когда выполните его; оно расширяет поверхность атаки.

Одного этого блока недостаточно: `docker-compose.yml` определяет только `edge` и
`data`, поэтому сети мониторинга, по которой сборщик метрик мог бы достучаться до
шлюза, не существует. Добавьте её и подключите к ней шлюз:

```yaml
  gateway:
    networks: [edge, monitoring]

networks:
  monitoring:
    external: true # created and owned by the monitoring stack
```

**Сегодня ничто в этом репозитории не потребляет `/metrics`** - ни конфигурации
сбора, ни правил алертов, ни дашбордов. Самое ценное правило, которое стоит
добавить первым, - правило на `ingest_last_success_age_seconds`, потому что оно
срабатывает _до_ истечения 26-часового бюджета `/readyz` и является единственным,
что позволило бы поймать пропущенный ночной импорт, пока ещё есть время его
перезапустить.

`/healthz` (живость процесса) и `/readyz` (живость плюс база данных плюс свежесть импорта)
остаются публичными: они не несут данных, а мониторинг портала - внешний вызывающий
(TZ §7 «проверка живости для мониторинга портала»). Направьте проверку ротации портала
на `/healthz` - почему `/readyz` для этой задачи неподходящая проба, см. в примечании
про `ingest_stale` выше.

## Логи

Каждый сервис пишет в stdout, а ротацией владеет рантайм контейнеров.
`docker-compose.yml` ограничивает каждый сервис значениями `max-size: 50m`,
`max-file: 5` - примерно 1 ГБ на весь стек. Без этого ограничения драйвер
`json-file`, используемый по умолчанию, растёт, пока диск хоста не заполнится, что
на однонодовой машине уносит с собой и базу данных. Если вы переходите на другой
драйвер логов, восстановите эквивалентное ограничение.

Строка cron для резервного копирования пишет в `/var/log/noplagiat-backup.log`,
который находится **вне** ротации рантайма контейнеров; заведите для него
отдельную запись `logrotate`.

> **Логи не в формате JSON.** `server/src/main.rs` инициализирует
> `tracing_subscriber::fmt()` без `.json()`, поэтому вывод идёт через
> человекочитаемый форматтер. Фича `json` вкомпилирована, но не используется.
> Любому конвейеру логов, ожидающему структурированные записи, - Loki, ELK,
> сборщику портала - сначала нужна эта однострочная правка; не планируйте
> конвейер приёма данных вокруг JSON, который сейчас не эмитируется.

## Ёмкость и расчёт дискового пространства

Рассчитано по измеренным значениям из `fixtures/load/RESULTS.md` на целевом
уровне TZ §7 в 250 тыс. (254 498 строк `checks`, 15 083 в `agg_monthly`,
~168 МБ) и по прогону восстановления от 30.08.2026 (дамп 4.0 МБ для хранилища в
61 423 строки):

| Потребитель              | Установившееся состояние                 | Примечания                                                                        |
| ------------------------ | ---------------------------------------- | --------------------------------------------------------------------------------- |
| том `pgdata`             | ~200 МБ при 250 тыс. проверок            | Плюс WAL и раздувание; закладывайте гигабайты, а не мегабайты.                    |
| ночные дампы             | ~15–20 МБ каждый, ~1 ГБ на 30+12         | Вне хоста. Срок хранения - 30 ежедневных + 12 ежемесячных.                        |
| прогон восстановления    | **удваивает живую базу данных**          | Временно и на том же экземпляре - оставьте под это запас.                         |
| том `reports`            | растёт неограниченно, по замыслу         | Неизменяемые снимки; никогда не подчищаются автоматически. Следите за ним.        |
| логи контейнеров         | потолок ~1 ГБ                            | Обеспечивается ограничениями `logging` выше.                                      |
| архив WAL (если включён) | до 288 × 16 МБ/сутки = **~4.6 ГБ/сутки** | При `archive_timeout=300` это накапливается даже на полностью простаивающей базе. |

Строка про WAL - та, что застаёт людей врасплох: пятиминутный `archive_timeout`
принудительно закрывает сегмент каждые пять минут независимо от того, писалось
что-нибудь или нет. Рассчитывайте объём архивного тома и политику его очистки до
включения архивирования, а не после.

## Позиция по доступности (TZ §7 «99% рабочее время»)

Сформулируйте это честно, а не унаследуйте цифру из TZ:

**Это однонодовый стек Compose без резервирования на каком-либо уровне.** Один
хост, один контейнер `postgres`, один `server`, один `web`, один `gateway`. Нет ни
реплики, ни автопереключения, ни балансировщика нагрузки. `restart:
unless-stopped` восстанавливает упавший _процесс_ за секунды, и это покрывает
типичный случай, - но каждое из перечисленного ниже является полным простоем на
всю свою длительность: перезагрузка хоста или аппаратный сбой, исчерпание диска,
неудавшаяся миграция при деплое (цикл падений), повреждение PostgreSQL, требующее
восстановления, и сам деплой.

При цели 99% за рабочий месяц из 5 дней по 8 часов (~173 ч) бюджет составляет
**~1.7 ч простоя в месяц**. Это достижимо для отказов уровня процесса и _не_
достижимо для восстановления из дампа, которое начинается от десятков минут и ни
разу не отрепетировано сквозным образом (см. «Восстановление поверх живой базы
данных»). Честная формулировка такова: 99% правдоподобны для всего, кроме
аварийного восстановления, а аварийное восстановление сейчас не ограничено
сверху, потому что RTO не согласован и не проверен.

Что должен проверять университетский прокси: **`GET /healthz`**, а не `/readyz`.
`/healthz` - это живость процесса, он отвечает 200 всегда, когда стек способен
обслуживать; `/readyz` намеренно возвращает 503 при устаревших данных, а это
условие свежести, с которым сайт прекрасно продолжает работать. Прокси, который
ротирует по `/readyz`, превращает пропущенный ночной импорт в простой, нанесённый
самому себе.

Чтобы улучшить это существенно, в порядке возрастания стоимости: ограничьте окно
деплоя отрепетированным откатом; добавьте реплику PostgreSQL и проверенную
процедуру её продвижения; поднимите два хоста приложения за университетским
прокси (приложение не хранит состояние нигде, кроме PostgreSQL, а планировщик
импорта уже использует консультативную блокировку ровно для этого, так что
запускать больше одного экземпляра безопасно).

## Обращение с секретами

Всё в этом списке приходит из хранилища секретов развёртывания и внедряется как
переменная окружения при старте контейнера. Ничто из этого не должно оказаться в Git, в
слое образа, в `docker build --build-arg` или в строке лога. `deploy/env.example` помечает
каждый из них как `SECRET`; `deploy/.env` предназначен только для локальных стеков и
занесён в gitignore.

| Секрет                                   | Примечания                                        |
| ---------------------------------------- | ------------------------------------------------- |
| `POSTGRES_PASSWORD` / `APP_DATABASE_URL` | URL содержит пароль внутри - ротируйте оба вместе |
| `APP_SOURCE_TOKEN`                       | bearer-токен для источника импорта вида API       |
| `APP_INGEST_PEPPER`                      | **не ротируется** - см. ниже                      |

### `APP_INGEST_PEPPER` отличается от остальных

Пеппер является ключом HMAC, который превращает идентификаторы авторов и проверяющих в
непрозрачные ссылки, хранимые в хранилище (ADR-008 §2). Это не учётные данные, которые
можно ротировать: его изменение перевыводит ключ для каждого будущего вычисления, поэтому
строки, импортированные после, больше не соединяются со строками, импортированными до.
Лестницы попыток ломаются, сопоставления `staff_units` перестают совпадать, и отказ
происходит **молча** - суммы по-прежнему сходятся, просто они неверны.

Поэтому:

- **Один пеппер на контур, на весь срок жизни этого контура.** У продакшена, стейджинга и
  разработки он свой у каждого, и они никогда не пересекаются.
- **Резервируйте его вместе с базой данных.** Восстановленный дамп нечитаем без того
  пеппера, которым он был получен. Храните его в собственной резервной копии хранилища
  секретов, а не в дампе базы данных.
- **Никогда в Git, никогда в базе данных, никогда в строке лога.** Сообщения об ошибках
  импортёра построены из типизированных вариантов именно по этой причине.
- Если когда-либо возникнет подозрение на его компрометацию, лекарство - полный повторный
  импорт исходных данных под новым пеппером в пустое хранилище, а не изменение на месте.

## Резервное копирование и восстановление

Политика (TZ §7 «резервное копирование БД дашборда не реже 1 раза в сутки»,
ARCHITECTURE.md §8): ночной `pg_dump` **плюс** непрерывное архивирование WAL, хранимые вне
тома Compose, зашифрованные согласно политике университета, с отрепетированным
восстановлением.

> **Текущее состояние - прочтите, прежде чем цитировать политику выше как факт.**
> Процедура здесь описана только для половины этой политики - ночного `pg_dump`.
> **Непрерывное архивирование WAL _не_ настроено этим репозиторием и нигде не
> работает.** Ничто в `docker-compose.yml` не задаёт `archive_mode`,
> `wal_level` или `archive_command`; раздел «Архивирование WAL» ниже - это
> процедура, **которую надлежит выполнить на хосте до продакшена**, а не
> описание чего-то уже существующего.
>
> Пока это не сделано, потеря данных в худшем случае составляет **один полный
> цикл импорта** - все импорты с момента последнего ночного дампа, - а не пять
> минут, как подразумевает примечание про `archive_timeout`. Восстановление на
> момент времени недоступно, и этот документ пока не содержит процедуры
> восстановления PITR (`restore_command` и `recovery_target_time` не описаны),
> так что включение архивирования - лишь первая половина этой работы.

Том Compose не является резервной копией. Как и снимок файловой системы с работающего
каталога данных PostgreSQL.

### Что резервируется

| Элемент                        | Как                                                                             |
| ------------------------------ | ------------------------------------------------------------------------------- |
| хранилище                      | ночной `pg_dump` (архив WAL: не настроен - см. выше)                            |
| `APP_INGEST_PEPPER`            | собственная резервная копия хранилища секретов - дамп сам по себе бесполезен    |
| снимки отчётов (том `reports`) | копирование на уровне файлов; они неизменяемы, поэтому достаточно инкрементного |

### Ночная логическая резервная копия

Выполняется против работающего стека. `--format=custom` обязателен - именно его читает
`pg_restore`, и он сжимает:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T postgres \
  sh -c 'pg_dump --format=custom --compress=zstd --username="$POSTGRES_USER" --dbname="$POSTGRES_DB"' \
  > "/srv/backup/noplagiat-$(date +%Y%m%d).dump"
```

> **Обёртка `sh -c '…'` и её одинарные кавычки несут смысловую нагрузку.**
> `$POSTGRES_USER` определена внутри контейнера, а не в оболочке оператора.
> Записанная без кавычек - или в двойных кавычках - она сначала раскроется
> оболочкой хоста и, поскольку ничто в этом документе её не экспортирует,
> подставится пустой строкой: `pg_dump --username=` сразу падает, а
> `CREATE DATABASE … OWNER` в прогоне восстановления ниже превращается в
> синтаксическую ошибку SQL. Одинарные кавычки откладывают раскрытие до
> контейнера, где переменная действительно существует. То же самое относится к
> каждой команде `exec -T postgres` в этом разделе.
>
> Используйте **ту же мажорную версию** `pg_dump`, что и у сервера. Более новый сервер со
> старым клиентом аварийно завершается с «server version mismatch»; запуск внутри
> контейнера `postgres`, как выше, гарантирует совпадение.

Проверяйте дамп сразу же - непроверенная резервная копия является догадкой.
Проверяйте её клиентом из **собственного образа** базы данных, по той же причине,
по которой там же снимается дамп; более старый `pg_restore` в `PATH` хоста
отвергает более новый заголовок архива и сообщает о повреждённой резервной копии,
которая на самом деле в порядке:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T postgres \
  pg_restore --list - < "/srv/backup/noplagiat-$(date +%Y%m%d).dump" > /dev/null \
  && echo "dump readable"
```

Срок хранения: держите 30 ежедневных и 12 ежемесячных копий, зашифрованных при хранении.
Копируйте их за пределы хоста базы данных; резервная копия на том же диске, что и база
данных, не переживёт тот отказ, ради которого она существует.

### Архивирование WAL (восстановление на момент времени) - НАСТРОИТЬ НА ХОСТЕ

**Сегодня не настроено.** Всё в этом разделе - процедура включения, и ничто из
неё не действует, пока кто-нибудь этого не сделает. `pg_dump` даёт вам прошлую
ночь; архивирование WAL дало бы любую секунду с тех пор. Включите его на сервисе
`postgres`, добавив переопределение команды в `docker-compose.yml`:

```yaml
command: >-
  postgres
  -c wal_level=replica
  -c archive_mode=on
  -c archive_command='test ! -f /srv/wal/%f && cp %p /srv/wal/%f'
  -c archive_timeout=300
```

и смонтируйте `/srv/wal` с долговременного хранилища вне тома `pgdata`. `archive_timeout=300`
ограничивает потерю данных в худшем случае пятью минутами даже тогда, когда база простаивает.

Базовая резервная копия для PITR - это `pg_basebackup`, а не `pg_dump`:

```bash
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T postgres \
  sh -c 'pg_basebackup --format=tar --gzip --wal-method=fetch --pgdata=- --username="$POSTGRES_USER"' \
  > "/srv/backup/base-$(date +%Y%m%d).tar.gz"
```

> `--wal-method=fetch`, а не `stream`: PostgreSQL отказывается стримить WAL в
> режиме tar на stdout (`cannot stream write-ahead logs in tar mode to stdout`),
> поэтому форма этой команды со `stream` падает при каждом запуске. `fetch`
> вместо этого собирает нужные сегменты в конце, а значит сервер всё ещё должен
> их удерживать - дайте `wal_keep_size` достаточный запас на время базовой
> резервной копии либо пишите в каталог через `--pgdata=/srv/backup/base` и
> оставьте `stream`.

Подчищайте архивированный WAL только относительно проверенной базовой резервной копии;
удаление сегмента, который ещё нужен базовой копии, молча делает эту копию
невосстановимой.

### Планирование запусков

**Linux (cron)** - `/etc/cron.d/noplagiat-backup`:

```cron
CRON_TZ=Asia/Almaty
# m  h  dom mon dow  user  command
  30 3  *   *   *    root  /usr/local/bin/noplagiat-backup.sh >> /var/log/noplagiat-backup.log 2>&1
```

03:30, **после** тика импорта в 02:00, чтобы каждый ночной дамп содержал импорт
этой ночи. Стоит проговорить, что именно это заменяет, потому что оба пункта были
неверны:

- **Тик приложения не следует за часами хоста.** Он прибит в коде к
  фиксированному числовому смещению `+05:00`, а не к именованной зоне
  (`server/crates/ingest/src/scheduler.rs`), поэтому на хосте в UTC - а это
  значение по умолчанию для большинства Linux-серверов - 02:00 +05:00 приходится
  на **21:00 UTC предыдущего дня**. Неуточнённое «01:30 по местному времени»
  поэтому попадает на 4.5 ч _позже_ импорта на хосте в UTC, а не за 30 мин до
  него. `CRON_TZ` выше сводит оба в одну систему отсчёта; проверьте хост через
  `timedatectl`, прежде чем доверять любому из них. Установка переменной
  окружения `TZ` в контейнере **не** сдвинет тик - смещение вкомпилировано, и
  добавление `TZ` в убеждении, что это сработает, является ловушкой.
- **Снятие дампа до импорта было задом наперёд.** Это гарантировало, что в каждой
  ночной резервной копии не хватает данных самой последней ночи, что в сочетании
  с отсутствующим архивом WAL доводит реальную потерю в худшем случае до ~26 ч
  импортов. `pg_dump` снимает MVCC-снимок и не блокирует пишущих, поэтому
  избегание «перекрытия» никогда не было причиной корректности планировать его
  раньше.

**Windows (планировщик заданий)** - для развёртывания на хосте под Windows:

```powershell
$action  = New-ScheduledTaskAction -Execute "pwsh.exe" `
             -Argument "-NoProfile -File C:\noplagiat\backup.ps1"
$trigger = New-ScheduledTaskTrigger -Daily -At 01:30
$principal = New-ScheduledTaskPrincipal -UserId "SYSTEM" -RunLevel Highest
Register-ScheduledTask -TaskName "noplagiat-backup" -Action $action `
  -Trigger $trigger -Principal $principal -Description "Nightly pg_dump of the analytics warehouse"
```

Какой бы планировщик ни использовался, алертьте на **отсутствие**: задание резервного
копирования, переставшее запускаться, делает это молча, и отказ обнаруживается только
тогда, когда потребуется восстановление.

### Прогон восстановления

Выполняйте его не реже раза в квартал и после любого изменения конвейера резервного
копирования. Он восстанавливает во **временную** базу данных, никогда поверх живой.

> **Что этот прогон доказывает и чего не доказывает.** Он доказывает, что дамп
> читаем и что число строк в нём переживает полный цикл. Он **не** доказывает
> продакшен-путь восстановления: он восстанавливает во временную базу данных **на
> том же экземпляре** - временно удваивая занимаемое живой базой место на диске и
> добавляя ей нагрузку - и передаёт `--no-owner --no-privileges`, поэтому
> владение и права никогда не задействуются. `pg_dump` одной базы данных также не
> несёт ролей и глобальных объектов; восстановление воспроизводит роль для входа
> лишь потому, что entrypoint Compose пересоздаёт `POSTGRES_USER` на свежем томе.
> Добавьте `pg_dumpall --globals-only` в ночное задание, если эта гарантия уровня
> контейнера когда-нибудь перестанет действовать.

```bash
# 0. Выберите дамп для проверки и убедитесь, что клиент совпадает с мажорной версией сервера.
#    $DUMP - путь на ХОСТЕ: он перенаправляется в контейнер, а не читается внутри него.
DUMP=/srv/backup/noplagiat-20260830.dump
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T postgres pg_dump --version

# 1. Зафиксируйте исходные показатели, которые восстановление должно воспроизвести.
#    Одинарные кавычки: $POSTGRES_USER / $POSTGRES_DB раскрываются КОНТЕЙНЕРОМ.
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T postgres \
  sh -c 'psql -U "$POSTGRES_USER" -d "$POSTGRES_DB" -c
  "SELECT (SELECT count(*) FROM checks) checks,
          (SELECT count(*) FROM agg_monthly) agg,
          (SELECT count(*) FROM staff_units) staff,
          (SELECT max(finished_at) FROM ingest_batches) newest_batch;"'

# 2. Создайте временную базу данных.
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T postgres \
  sh -c 'psql -U "$POSTGRES_USER" -d postgres -c "CREATE DATABASE restore_drill OWNER \"$POSTGRES_USER\";"'

# 3. Восстановите в неё. --exit-on-error превращает частичное восстановление в отказ.
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T postgres \
  sh -c 'pg_restore --username="$POSTGRES_USER" --dbname=restore_drill \
             --no-owner --no-privileges --exit-on-error' < "$DUMP"

# 4. Проверьте: те же четыре показателя, но против восстановленной базы данных.
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T postgres \
  sh -c 'psql -U "$POSTGRES_USER" -d restore_drill -c
  "SELECT (SELECT count(*) FROM checks) checks,
          (SELECT count(*) FROM agg_monthly) agg,
          (SELECT count(*) FROM staff_units) staff,
          (SELECT max(finished_at) FROM ingest_batches) newest_batch;"'

# 5. Удалите временную базу данных. Прогон, оставляющий после себя копию, - это баг разрастания данных.
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T postgres \
  sh -c 'psql -U "$POSTGRES_USER" -d postgres -c "DROP DATABASE restore_drill;"'
```

Шаг 4 должен точно совпасть с шагом 1 - с одной оговоркой о том, как именно он
совпадает. `agg_monthly` - материализованное представление, а `pg_dump` **не**
копирует строки материализованного представления: он выгружает определение плюс
`REFRESH MATERIALIZED VIEW` в секции post-data, поэтому эти строки
пересчитываются из восстановленных фактов, а не восстанавливаются. Совпадающее
число строк, таким образом, свидетельствует, что и факты, и определение
представления уцелели, - а это именно то, что вы хотите знать, - но не
свидетельствует, что хоть какие-то строки были перенесены в дампе. Если оно
возвращается пустым, выполните `SELECT refresh_aggregates();` - который обновляет
все три материализованных представления, а не только это - и разберитесь, прежде
чем доверять конвейеру.

### Восстановление поверх живой базы данных

Прогон намеренно никогда не трогает живую базу данных, поэтому фактический путь
аварийного восстановления остаётся неотрепетированным. Этот путь **здесь ещё не
записан и должен быть записан до ввода в эксплуатацию.** Как минимум он обязан
сначала останавливать `server`: пока контейнер работает, стартовые миграции и
ночной тик оба пишут, и любое из этого против наполовину восстановленной базы
усугубляет инцидент. `restart: unless-stopped` означает, что остановка контейнера

- это явный `stop`, а не kill. Ни RPO, ни RTO для этого сервиса не согласованы;
  согласуйте оба, затем отрепетируйте против `postgres:18-alpine`.

Прогон не доказывает, что пеппер уцелел. Отдельно убедитесь, что хранилище секретов
по-прежнему содержит пеппер для того контура, откуда пришёл дамп, - восстановленное
хранилище, в которое нельзя ничего добавить, это лишь половина восстановления.

## Отчёты по реальным данным за 2024/25 и 2025/26 уч. г. (W4.3, TZ §10.9)

Исходные выгрузки в `stats/` содержат персональные данные. Они занесены в gitignore и
должны там оставаться; **обезличивает их именно конвейер импорта** (ADR-008 §10), поэтому
шагом обезличивания является сам импорт, а не предварительная обработка.

Выполняйте это на машине, где уже есть `stats/`, против **продакшен-**пеппера - иначе
производные ссылки не совпадут ни с чем, что содержит продакшен-хранилище.

```bash
# 1. Продакшен-пеппер из хранилища секретов, только в этой оболочке.
#    Никогда не делайте ему `export` в профиль и никогда не выводите его через echo.
read -rs APP_INGEST_PEPPER && export APP_INGEST_PEPPER
export APP_DATABASE_URL='postgres://...'      # целевое хранилище

# 2. Импорт через настоящий конвейер, по одному вызову на каждое дерево источника.
#    --dir принимает корень, содержащий каталоги YYYY-YYYY, либо один из них.
#    Запускайте бинарь, который уже есть В развёрнутом образе (см. примечание ниже);
#    смонтируйте или скопируйте `stats/` по пути, доступному контейнеру на чтение.
docker compose --env-file deploy/.env -f deploy/docker-compose.yml exec -T server \
  ingest-csv --dir /srv/stats --source csv-backfill-2024
```

> Используйте `ingest-csv` из образа, а не `cargo run`. `deploy/Dockerfile.server`
> поставляет `ingest-csv` (и `generate-report`) рядом с сервером именно ради этой
> процедуры, чтобы бэкфилл выполнялся той же сборкой, что и развёртывание, и с
> пеппером развёртывания. Форма `cargo run --release`, которую эта строка несла
> раньше, требовала полного тулчейна Rust и релизной компиляции с нуля **на
> машине, где лежат продакшен-выгрузка `stats/` и продакшен-пеппер**, - тулчейна,
> которому там больше незачем находиться. Оставьте `cargo run` только для рабочей
> станции разработчика.

`ingest-csv` завершается с ненулевым кодом, если хоть одна партия отказала, поэтому
проверяйте код возврата, а не читайте вывод.

```bash
# 3. Сверьте с контрольными показателями, прежде чем что-либо генерировать.
psql "$APP_DATABASE_URL" -c \
  "SELECT academic_year, count(*) FROM checks GROUP BY 1 ORDER BY 1;"
```

Сравните с итогами «Совершенных проверок» в исходном `system-usage.csv`
(2024/25: 5 457). Расхождение объясняется **письменно** до того, как отчёты уйдут:
`ingest_batches.errors` перечисляет отклонённые строки и причины. При несовпадении не
продолжайте.

```bash
# 4. Сгенерируйте оба годовых отчёта, обе обязательные локали, через админский API.
#    (Планировщик 1 сентября делает ровно это автоматически; здесь ручной путь
#    для уже прошедшего года.)
#
#    $SESSION - cookie админской сессии в форме `name=value`. Получите его, войдя
#    в /app пользователем с ролью администратора и скопировав cookie `np_session`;
#    эти эндпоинты закрыты RBAC и без него отвечают 401. `set -e` важен: без него
#    незаданный cookie приводит к 401 на всех четырёх вызовах, --fail каждый раз
#    возвращает 22, цикл всё равно «завершается», а шаг 5 показывает пустой
#    каталог без единой ошибки где-либо.
set -e
for AY in 2024 2025; do
  for LOCALE in ru kk; do
    curl --fail --cookie "$SESSION" -X POST \
      "$APP_PUBLIC_BASE_URL/api/admin/reports/generate" \
      -H 'content-type: application/json' \
      -d "{\"kind\":\"annual\",\"period_start\":\"$AY-09-01\",\"period_end\":\"$((AY+1))-08-31\",\"locale\":\"$LOCALE\"}"
  done
done
```

Каждый вызов записывает PDF и XLSX в `APP_REPORTS_DIR` и заносит неизменяемую строку в
`report_snapshots`. Генерация **не** является публикацией: отчёты остаются вне публичного
контура, пока администратор их не опубликует (`POST /api/admin/reports/{id}/publish`).

> **Проверяйте, что обе локали созданы, каждый раз - в том числе после
> автоматического запуска.** Планировщик 1 сентября срабатывает в 03:00 +05:00, и
> его защита от повторного выполнения привязана к учебному _году_, а не к паре
> «год + локаль». Падение или перезапуск между генерациями RU и KK оставляет год
> помеченным как выполненный при отсутствующей KK, и **ни один последующий тик её

## Масштаб: требование 5× (TZ §7)

TZ §7 требует, чтобы система выдержала «рост объёма данных минимум в 5 раз (до 250 000+
записей) без существенной переработки». Это спроектировано, а не оставлено на надежду, и
это измеряется еженощно:

- Пути запросов читают свёртки `agg_monthly`, поэтому их стоимость зависит от произведения
  «месяцы × группы», а не от числа строк таблицы фактов (ARCHITECTURE.md §7). Переход с
  50 тыс. на 250 тыс. строк меняет таблицу фактов, а не агрегат.
- `.github/workflows/nightly-load.yml` каждую ночь засевает 250 000 строк через настоящий
  импортёр и падает при p95 `/api/public/summary` ≥ 300 ms.
- `fixtures/load/RESULTS.md` фиксирует измеренные значения и длительность обновления
  материализованного представления - ту стоимость, которая растёт вместе с таблицей фактов
  и которую задержка запросов иначе скрыла бы (PLAN.md R6).

Когда хранилище приблизится к следующему порядку величины, вот к чему стоит обратиться в
первую очередь - именно в этом порядке, и ничто из этого не требуется сегодня:

1. `REFRESH MATERIALIZED VIEW CONCURRENTLY` для `agg_monthly` (уникальный индекс под это уже
   есть), чтобы обновление перестало блокировать читателей.
2. Партиционирование `checks` по учебному году. Импортёр уже пишет по одной партии на год, а
   каждый запрос ограничен по времени, поэтому ключ партиционирования - тот, что уже
   используется.
3. Реплика для чтения под публичный контур, который кэшируем и по замыслу терпит отставание
   реплики (`Cache-Control: public, max-age=3600`).
