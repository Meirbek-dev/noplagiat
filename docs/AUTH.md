# Аутентификация и авторизация

Справочник по входу во внутренний контур: как устроен вход, кто заводит учётные
записи, что несёт сеанс и какие гарантии закреплены тестами.

**Решение и его обоснование** - [ADR-017](adr/017-local-accounts.md) (что и
почему; заменил поток OIDC из [ADR-014](adr/014-oidc-and-internal-surface.md)
§1–§3). **Эксплуатационные процедуры** - [deploy/RUNBOOK.md](../deploy/RUNBOOK.md),
раздел «Учётные записи и первый администратор». Этот документ - как оно работает.

---

## 1. Модель в одном абзаце

Вход - это **логин и пароль**, хранящиеся в таблице `users` той же базы, что и
хранилище. Пароль хешируется Argon2id. Успешный вход выдаёт непрозрачный
идентификатор сеанса в cookie `np_session`; всё остальное - личность, роли,
область видимости - читается из базы на каждом запросе. Учётные записи заводит
**только** CLI `manage-users` на хосте развёртывания.

Чего здесь **нет** и не появится случайно:

| Нет                                      | Следствие                                                                          |
| ---------------------------------------- | ---------------------------------------------------------------------------------- |
| поставщика идентичности (OIDC/SAML/LDAP) | нечего настраивать, нечего ждать от ИТ-службы, нечему сломаться при ротации ключей |
| формы регистрации                        | посторонний не может завести себе запись                                           |
| маршрута восстановления пароля           | нет оракула существования учётных записей; сброс - через администратора            |
| HTTP-маршрута, создающего запись         | ошибка в HTTP-поверхности не может выпустить администратора                        |
| JWT и подписанных cookie                 | отзыв роли действует со следующего запроса, а не по истечении токена               |

Публичный контур (`/`, `/embed`, `/api/public/*`) аутентификации не требует
вообще - он анонимен по построению (ТЗ §4.1).

## 2. Жизненный цикл

```
  оператор на хосте                браузер                        сервер
  ─────────────────                ───────                        ──────
  manage-users create-user ─────────────────────────────────► INSERT users
        (Argon2id хеш)                                        (+ user_roles)

                          логин + пароль ──► POST /api/auth/login
                                                  │ verify(Argon2id)
                                                  │ DELETE предъявленного сеанса
                                                  │ INSERT sessions
                          ◄── Set-Cookie: np_session=<64 hex>
                              { username, role, roles, scope, csrf_token }

                          GET /api/internal/... ──► session_auth
                            Cookie: np_session          │ SELECT sessions (не истёк)
                                                        │ SELECT users (active)
                                                        │ SELECT user_roles  ← каждый раз
                                                        ▼
                                                   CurrentUser → Scope → SQL

                          POST /api/auth/logout ──► DELETE sessions
                          ◄── Set-Cookie: np_session=; Max-Age=0
```

Ключевое свойство третьего шага: **гранты перечитываются на каждом запросе**.
Отзыв роли или деактивация записи действуют со следующего HTTP-запроса, а не со
следующего входа.

## 3. Учётные записи: CLI `manage-users`

Единственный способ создать запись или задать пароль. Бинарник лежит в том же
образе, что и сервер (`deploy/Dockerfile.server`), и сам применяет миграции,
поэтому на свежем стенде его можно запустить до первого старта сервера.

CLI читает ровно две переменные окружения: `APP_DATABASE_URL` (обязательно) и
`APP_ADMIN_PASSWORD` (необязательно, см. §3.3). Флага `--database-url` нет:
адрес базы - свойство стенда, а не аргумент команды. Ненулевой код возврата на
любой ошибке - на него можно опираться в скрипте развёртывания.

### 3.1. Откуда берётся `APP_DATABASE_URL`

Бинарник в самом начале выполняет `dotenvy::dotenv()`, то есть ищет файл `.env`
в **текущем рабочем каталоге и выше по дереву**. `cargo run` не переходит в
каталог пакета - процесс наследует тот каталог, из которого вы его запустили.
Поэтому из корня репозитория `server/.env` не виден: в корне `.env` нет, и
команда падает с `required environment variable APP_DATABASE_URL is not set`.

| Откуда запускаете               | Команда                                        | Откуда берётся адрес базы            |
| ------------------------------- | ---------------------------------------------- | ------------------------------------ |
| стенд Compose                   | `... exec server manage-users <команда>`       | окружение контейнера (`deploy/.env`) |
| дерево исходников, из `server/` | `cargo run --bin manage-users -- <команда>`    | `server/.env`, подхватывается сам    |
| дерево исходников, из корня     | то же плюс `--manifest-path server/Cargo.toml` | переменную задаёте вы                |

```bash
# 1. стенд Compose - переменные уже в окружении контейнера
podman compose --env-file deploy/.env -f deploy/docker-compose.yml \
  exec server manage-users <команда>
# docker compose - та же строка с `docker` вместо `podman`
```

```bash
# 2. дерево исходников, из каталога server/ - server/.env подхватывается сам
cd server
cargo run --bin manage-users -- <команда>
```

```powershell
# 3. дерево исходников, из корня репозитория - переменную задаёте вы (PowerShell)
$env:APP_DATABASE_URL = 'postgres://noplagiat:noplagiat@localhost:5432/noplagiat'
cargo run --manifest-path server/Cargo.toml --bin manage-users -- <команда>
```

```bash
# то же в POSIX-оболочке
export APP_DATABASE_URL='postgres://noplagiat:noplagiat@localhost:5432/noplagiat'
cargo run --manifest-path server/Cargo.toml --bin manage-users -- <команда>
```

**Пишите `--` всегда.** Он отделяет аргументы бинарника от аргументов cargo.
Без него команда чаще всего тоже проходит - cargo отдаёт бинарнику всё, что
следует за первым позиционным аргументом, а первым идёт имя команды
(`create-user`), - но флаг сразу после `--bin manage-users` cargo попытается
разобрать как свой и откажет.

**База, к которой вы подключились, - та, которую CLI мигрирует.** Перед работой
он применяет миграции (это и позволяет завести администратора до первого старта
сервера), поэтому опечатка в адресе не просто «не находит» запись, а создаёт
схему в чужой базе. У compose-стенда порт `postgres` наружу не опубликован -
единственный опубликованный порт стека шлюзовой, - поэтому с хоста к его базе
подключиться нельзя, и для него годится только вариант с `exec server`.

### 3.2. Команды

| Команда                   | Обязательные           | Необязательные                                                                      |
| ------------------------- | ---------------------- | ----------------------------------------------------------------------------------- |
| `create-user`             | `--username`           | `--role`, `--faculty`, `--department`, `--email`, `--display-name`, `--no-password` |
| `set-password`            | `--username`           | -                                                                                   |
| `grant`                   | `--username`, `--role` | `--faculty`, `--department`                                                         |
| `revoke`                  | `--username`, `--role` | `--faculty`, `--department`                                                         |
| `list`                    | -                      | -                                                                                   |
| `activate` / `deactivate` | `--username`           | -                                                                                   |

Значения по умолчанию у `create-user`: `--email` = `<username>@local.invalid`
(непрозрачный нерутируемый адрес - выдумывать настоящий хуже),
`--display-name` = логин.

**Логин** - ASCII-буквы, цифры и `.`, `-`, `_`, `@`. Пробелы обрезаются;
регистр не важен при входе, но хранится как введён. `Admin` и `admin` - одна
запись, а не две (уникальный индекс по `lower(username)`).

### 3.3. Откуда берётся пароль

1. **Интерактивно** - приглашение с отключённым эхом терминала, с повтором для
   подтверждения на `create-user` и `set-password`.
2. **Неинтерактивно** - переменная окружения `APP_ADMIN_PASSWORD`. Используется,
   когда на stdin нет терминала (CI, скрипт провижининга). Подтверждение не
   запрашивается.

**Аргументом пароль не передаётся.** Флага `--password` нет, и он отклонён
по имени с объяснением: аргумент оказался бы в истории оболочки и в выводе `ps`,
видимом любому другому пользователю хоста.

### 3.4. Три правила, которые CLI навязывает

- **`create-user` не является upsert.** Повторный вызов для существующего логина -
  ошибка, а не молчаливая перезапись e-mail и пароля живой записи. Нужный
  инструмент для этого - `set-password`.
- **Роль подразделения обязана называть подразделение.** `--role dean` без
  `--faculty` и `--role dept_head` без `--department` отклоняются: такой грант
  выглядел бы выданным и не показывал бы ничего (§6).
- **Общеуниверситетская роль не принимает подразделение.** `--role admin
--faculty FAC03` отклоняется, потому что оператор, который это написал, думает,
  что сужает грант, - а это не так.

### 3.5. Рецепты

Ниже команда записана голым именем `manage-users` - так она выглядит внутри
контейнера; в дереве исходников подставьте свой префикс из §3.1.

```bash
# первый администратор на свежем стенде
manage-users create-user --username admin --role admin

# декан факультета и заведующий кафедрой
manage-users create-user --username dean.fac03 --role dean      --faculty FAC03
manage-users create-user --username head.dep11 --role dept_head --department DEP11

# запись без пароля: существует, может держать гранты, войти нельзя
manage-users create-user --username service.ro --role compliance --no-password

# сброс пароля (закрывает все живые сеансы этой записи)
manage-users set-password --username dean.fac03

# вторая роль той же записи; гранты аддитивны
manage-users grant --username dean.fac03 --role ethics

# закрыть доступ, не удаляя запись и её историю аудита
manage-users deactivate --username dean.fac03

# кто есть и с какими ролями
manage-users list

# неинтерактивно (провижининг)
APP_ADMIN_PASSWORD='...' manage-users create-user --username admin --role admin
```

`set-password` и `deactivate` **завершают все живые сеансы** этой записи в том же
вызове: смена пароля, после которой прежняя cookie ещё работает, - это не смена
пароля.

Роли можно выдавать и отзывать также через админ-раздел (`/admin/roles`,
`POST`/`DELETE /api/admin/roles`, ТЗ §4.6) - при условии, что запись уже
существует. Пароль через HTTP не задаётся никогда.

## 4. HTTP-поверхность

Три маршрута. Контракт - `contracts/openapi.json` (генерируется из типов Rust,
править вручную нельзя).

### `POST /api/auth/login`

```jsonc
// запрос
{ "username": "admin", "password": "..." }

// 200 - тот же документ, что отдаёт /me
{
  "username": "admin",
  "role": "admin",                    // самая широкая из held-ролей, или null
  "roles": [{ "role": "admin", "scope_faculty_code": null, ... }],
  "scope": { "kind": "all", "faculty_id": null, "department_id": null },
  "request_access_path": "/app/request-access",
  "csrf_token": "…64 hex…"
}
```

Плюс `Set-Cookie: np_session=…` (§5). Тело намеренно совпадает с `/me`, чтобы
клиенту не требовался второй круг за собственными правами.

| Код   | Когда                                                                                                                  |
| ----- | ---------------------------------------------------------------------------------------------------------------------- |
| `200` | вход выполнен                                                                                                          |
| `401` | **любой** отказ: неизвестный логин, неверный пароль, пароль не задан, запись деактивирована - один и тот же текст (§7) |
| `422` | пустой `username` или `password` - это ошибка поля, а не попытка входа                                                 |
| `429` | превышен ограничитель частоты; ответ несёт `Retry-After`                                                               |

### `POST /api/auth/logout`

Требует сеанс и CSRF-токен. Отвечает `{ "next_path": "/login" }` и cookie с
`Max-Age=0`. `next_path` всегда один и тот же: завершать второй сеанс негде.

| Код   | Когда                                              |
| ----- | -------------------------------------------------- |
| `200` | сеанс закрыт                                       |
| `401` | сеанса нет, он неизвестен или истёк                |
| `403` | заголовок `x-csrf-token` отсутствует или не совпал |

### `GET /api/auth/me`

Личность и права текущего сеанса; тело как у `login`. `401`, если сеанса нет.
Безопасный метод, поэтому CSRF-токен не нужен.

**Фронтенд трактует `401` от `/me` не как ошибку, а как анонимный ответ**
(`authApi.me` возвращает `null`), иначе на странице входа возникала бы граница
ошибки вместо формы.

## 5. Сеанс и CSRF

| Свойство   | Значение                                                                                      |
| ---------- | --------------------------------------------------------------------------------------------- |
| Cookie     | `np_session`                                                                                  |
| Содержимое | 32 байта из CSPRNG ОС, hex → 64 символа. Больше ничего: ни полезной нагрузки, ни подписи      |
| Атрибуты   | `Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=<TTL>`                                       |
| TTL        | `APP_SESSION_TTL_SECONDS`, по умолчанию `43200` (12 ч - один рабочий день)                    |
| Хранение   | таблица `sessions` (миграция 0004): `id`, `user_id`, `created_at`, `expires_at`, `csrf_token` |
| CSRF-токен | отдельные 32 байта, отдаются в теле `login`/`me`, предъявляются заголовком `x-csrf-token`     |

Почему так:

- **`Secure` выставляется безусловно.** Браузер примет такую cookie на
  `http://localhost` (это secure context), но **молча отбросит** на
  plain-HTTP-хосте с настоящим именем. Стенд на `http://staging.example/`
  поэтому принимает верный пароль и ведёт себя так, будто вход ничего не сделал.
  На любом не-localhost хосте TLS обязателен.
- **`SameSite=Lax`** блокирует межсайтовые POST-запросы; CSRF-токен - второй
  замок, он не в cookie (прочитать со стороннего сайта нельзя) и не угадывается.
- **CSRF-токен хранится в строке сеанса, а не выводится из его идентификатора**,
  чтобы утечка одного не давала второго.
- **Ротация при входе.** Cookie, предъявленная на запросе входа, удаляется, а
  новый идентификатор генерируется заново: подложенный заранее сеанс к моменту
  входа жертвы уже мёртв (session fixation).
- **Уборка истёкших строк** выполняется попутно при входе, а не по таймеру:
  сеансы живут часы, входы случаются не реже, и одной фоновой задачей меньше.

Проверка CSRF применяется ко всем небезопасным методам (`POST`, `PUT`, `PATCH`,
`DELETE`). `POST /api/auth/login` - единственное исключение: это запрос,
который **создаёт** токен, поэтому предъявлять ещё нечего.

## 6. Роли и область видимости

Шесть ролей ТЗ §5. Грант - это пара `(роль, область)`; запись может держать
несколько, и они **аддитивны**.

| Роль         | Область видимости грантa            | Внутренний контур | Экраны                   |
| ------------ | ----------------------------------- | ----------------- | ------------------------ |
| `staff`      | нет                                 | ✗ (403)           | публичный контур         |
| `dept_head`  | своя кафедра (**обязательна**)      | ✓ кафедра         | разделы кроме эскалаций  |
| `dean`       | свой факультет (**обязателен**)     | ✓ факультет       | разделы кроме эскалаций  |
| `ethics`     | вся организация, либо подразделение | ✓                 | + эскалации              |
| `compliance` | вся организация, либо подразделение | ✓                 | + эскалации              |
| `admin`      | вся организация, либо подразделение | ✓                 | + эскалации + `/admin/*` |

Как несколько грантов сворачиваются в одну область:

- **Побеждает самый широкий** грант (`all` > `faculty` > `department`); при
  равенстве - меньший id подразделения, чтобы результат был детерминирован.
- **`staff` не даёт внутренней области вообще.** ТЗ §5 отводит ППС публичный
  контур; грант `staff` в одиночку - это `403` на каждом внутреннем маршруте.
- **Роль подразделения без подразделения - «данных не видно», а не «видно всё».**
  Для декана или заведующего NULL-область - это неверно заполненный грант, и
  безопасное его прочтение - _ничего_, иначе наполовину заполненная форма была бы
  повышением привилегий. Именно поэтому CLI отказывается создавать такой грант
  (§3.4).

Область видимости не является рекомендацией: `RbacScope` - экстрактор, и **каждая**
функция запроса внутреннего контура в крейте `db` принимает `Scope` параметром;
фильтрация выполняется в SQL. Пути «запросить внутренние данные без области» в
коде не существует (AGENTS.md инвариант #3).

Два дополнительных гейта поверх области:

- `require_admin` - `/api/admin/*` только для `admin`.
- `require_section_role` - читает колонку `allowed` реестра маршрутов в
  `api::rbac`, поэтому `GET /api/internal/escalations` закрыт для декана
  строкой реестра, а не второй копией правила в обработчике.

Роль влияет ещё на одно: `Screening::for_role` решает, видит ли вызывающий
точные числа или прошедшие k-анонимное подавление. Пять ролей с областью видят
точные внутри своей области; `staff` и безролевые - подавленные.

## 7. Пароли

**Хранение.** Argon2id с параметрами по умолчанию крейта `argon2` (19 МиБ,
2 прохода, 1 полоса - второй рекомендованный набор RFC 9106). В колонке
`users.password_hash` лежит **PHC-строка** (`$argon2id$v=19$m=…,t=…,p=…$соль$хеш`),
а не голый дайджест: параметры едут вместе с хешем, поэтому поднять стоимость
позже можно без блокировки существующих учётных записей. Соль - своя на каждую
запись, поэтому две одинаковые парольные фразы дают разные хеши.

**Политика - только длина:** минимум 12 символов, максимум 256. Требований к
набору символов нет намеренно (NIST SP 800-63B §5.1.1.2: значение имеет длина,
а не обязательная цифра). Длина считается в символах, а не в байтах, иначе
кириллическая парольная фраза оценивалась бы вдвое длиннее, чем читается.

**`password_hash IS NULL` означает «войти нельзя».** Запись существует, может
держать гранты и видна в админ-разделе, но ничего не проходит проверку. В этом
состоянии находятся записи, созданные с `--no-password`, и каждая строка,
перенесённая миграцией 0006 из эпохи SSO.

### Один отказ на все случаи

Неизвестный логин, неверный пароль, пароль не задан, запись деактивирована -
**один `401` с одним текстом**. Различать их значило бы превратить маршрут в
оракул существования логинов, а логины здесь названы по ролям сотрудников.

Это относится и ко времени ответа, что менее очевидно и легко сломать:

- Неизвестный логин всё равно оплачивает работу Argon2 против фиктивного хеша.
  Иначе «нет такого пользователя» возвращалось бы за микросекунды там, где
  неверный пароль стоит десятки миллисекунд.
- Деактивированная запись отбрасывается подстановкой `None` вместо хеша, и
  проверка на `None` **тоже** оплачивает эту работу. Иначе разница во времени
  сообщала бы, какие записи заблокированы.

### Ограничитель частоты

У `POST /api/auth/login` собственная корзина: **10 попыток подряд, далее одна
раз в четыре секунды** (`burst: 10`, `per_minute: 15`), по адресу клиента.
Превышение - `429` с заголовком `Retry-After`, и отказ происходит **в слое**, до
обращения к базе и до проверки Argon2.

Публичный ограничитель (`burst: 120`, `per_minute: 600`) намеренно щедр:
публичный контур кешируется на час, и легитимный посетитель делает один запрос
на раздел в час. Маршрут с паролем требует обратной формы, поэтому у него
отдельная корзина, а не общая.

## 8. Фронтенд

| Что                        | Где                                                  |
| -------------------------- | ---------------------------------------------------- |
| Форма входа                | `apps/web/src/routes/login.tsx`                      |
| Клиент сеанса              | `apps/web/src/lib/api-internal.ts` (`authApi`)       |
| Охрана внутреннего контура | `apps/web/src/routes/app/route.tsx` (`beforeLoad`)   |
| Охрана админки             | `apps/web/src/routes/admin/route.tsx` (`beforeLoad`) |
| Страница запроса доступа   | `apps/web/src/routes/app/request-access.tsx`         |
| Выход                      | `apps/web/src/components/internal/InternalShell.tsx` |

Куда попадает пользователь:

- **Анонимный** на `/app/*` или `/admin/*` → `/login?redirect=<куда шёл>`.
- **Аутентифицированный без внутренней роли** (в том числе `staff`) →
  `/app/request-access`. Это страница вошедшего пользователя, а не ошибка: у
  человека валидный сеанс, и ему нужно знать, что и у кого просить. Путь берётся
  из ответа сервера (`request_access_path`), а не дублируется в коде, поэтому
  охрана не зациклится, если он изменится.
- **Не-администратор** на `/admin/*` → в контур, который у него **есть**
  (`/app`), а не в тупик.

Клиентские проверки существуют **только ради UX**. Авторизацию обеспечивает
сервер: `/api/internal/*` и `/api/admin/*` откажут независимо от того, что решил
роутер, и матрица RBAC (446 случаев в `tests/rbac.rs`) - доказательство этого.

После входа кеш запросов очищается целиком (`queryClient.clear()`): каждый
закешированный ответ принадлежал предыдущей личности и не должен быть показан
новой.

Форма не подсказывает, какая половина неверна: `401` печатается как «Неверный
логин или пароль», `429` - как «Слишком много попыток входа». Пароль пробрасывается
в браузерный менеджер паролей через `autocomplete="username"` /
`autocomplete="current-password"`; остальные поля приложения остаются
`autocomplete="off"`.

## 9. Схема

```sql
users(
  id            BIGINT PK,
  username      TEXT NOT NULL,   -- UNIQUE по lower(username)
  password_hash TEXT NULL,       -- Argon2id PHC; NULL = войти нельзя
  email         TEXT NOT NULL,
  display_name  TEXT NOT NULL,
  active        BOOLEAN NOT NULL DEFAULT TRUE,
  sso_subject   TEXT NULL UNIQUE -- колонка эпохи SSO, см. ниже
)

user_roles(user_id FK, role role_kind, scope_faculty_id FK NULL, scope_department_id FK NULL,
           UNIQUE NULLS NOT DISTINCT (user_id, role, scope_faculty_id, scope_department_id))

sessions(id BYTEA PK CHECK octet_length = 32, user_id FK ON DELETE CASCADE,
         created_at, expires_at, csrf_token BYTEA CHECK octet_length = 32)
```

`sso_subject` **осталась намеренно**. Миграция 0006 - фаза expand цикла
expand→migrate→contract: она добавила `username`/`password_hash`, перенесла
значения и сняла с `sso_subject` ограничение NOT NULL, но не удалила колонку -
удаление является разрушающим шагом и по инварианту #6 AGENTS.md выполняется
отдельным изменением. Практическая польза переноса: запись, пришедшая когда-то
через SSO, сохранила свои гранты и историю аудита, и администратору достаточно
задать ей пароль.

Инвариант #1 AGENTS.md («никаких ПДн») здесь соблюдается так: `email` и
`display_name` - поля **служебной** учётной записи дашборда, которые ТЗ §6.1
выводит из-под запрета именно для того, чтобы можно было администрировать
гранты. Они появляются в админ-разделе и больше нигде: ни в одном аналитическом
ответе, ни в одной выгрузке, ни в одной строке лога. Журнал аудита пишет
`user_id` - ключ хранилища, а не адрес.

## 11. Диагностика

| Симптом                                                                                | Причина и что делать                                                                                                                                                                                                                                 |
| -------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Стенд поднялся, войти некем; в логе предупреждение об отсутствии записей               | Учётных записей нет - это ожидаемое состояние свежего развёртывания. `manage-users create-user --username admin --role admin`                                                                                                                        |
| Верный пароль принят, но пользователь остаётся анонимным                               | Cookie отброшена: `Secure` выставляется всегда, а хост не под TLS и не `localhost`. Терминируйте TLS перед шлюзом либо тестируйте на `localhost`                                                                                                     |
| `401` на верном пароле                                                                 | Запись заведена не в той базе, которую читает сервер: из дерева исходников `list` смотрит в локальную базу, а стенд - в свою, наружу не опубликованную (§3.1). Иначе запись деактивирована или `password_hash IS NULL` - `activate` / `set-password` |
| `429` на входе                                                                         | Ограничитель: 10 попыток, далее одна в 4 с с этого адреса. Дождитесь `Retry-After`. Если адрес общий за прокси - проверьте, что шлюз ставит `X-Forwarded-For`                                                                                        |
| `403` с текстом про `x-csrf-token`                                                     | Мутация без токена. Возьмите `csrf_token` из `/api/auth/me` и передайте заголовком                                                                                                                                                                   |
| `403` с указанием `/app/request-access`                                                | Сеанс валиден, но у записи нет роли с внутренней областью. Выдайте грант: `manage-users grant` или `/admin/roles`                                                                                                                                    |
| Пользователь вошёл, но разделы пусты, а грант «есть»                                   | Грант декана/заведующего без подразделения (заведён в обход CLI). Такая область читается как «данных не видно» - отзовите и выдайте заново с `--faculty`/`--department`                                                                              |
| `manage-users` жалуется на занятый логин                                               | `create-user` не является upsert - это защита от перезаписи живой записи. Нужен `set-password`                                                                                                                                                       |
| `manage-users: required environment variable APP_DATABASE_URL is not set`              | Переменной нет в окружении команды. `cargo run` наследует текущий каталог, а `.env` ищется в нём и выше по дереву, поэтому из корня репозитория `server/.env` не виден. Запускайте из каталога `server/` либо задайте переменную явно - §3.1         |
| `manage-users: failed to connect to PostgreSQL` / `timed out connecting to PostgreSQL` | Адрес ведёт не туда, куда вы думаете: локальная база не поднята, либо это адрес базы compose-стенда, чей порт наружу не опубликован. Для стенда есть только путь через `exec server` - §3.1                                                          |
| `no faculty ... in the dictionaries` / `no department ...`                             | Справочники пусты: коды подразделений появляются только после загрузки данных (`vp run seed` или ингест). До этого грант декана или заведующего создать нечем - заведите запись без `--role`, а грант выдайте позже через `grant`                    |
| Пользователь после смены пароля «выкинут» из приложения                                | Так и задумано: `set-password` завершает все сеансы записи                                                                                                                                                                                           |

## 12. Разработка и тесты

**Локально.** `vp run seed` заводит фикстурные учётные записи (общий список -
`fixtures/accounts.ts`, тот же, что читает e2e-набор); он вызывает тот же CLI и
передаёт ему `APP_DATABASE_URL` и `APP_ADMIN_PASSWORD` в окружении дочернего
процесса. Свою запись создайте тем же CLI - другого способа нет:

```powershell
cd server
cargo run --bin manage-users -- create-user --username admin --role admin
cargo run --bin manage-users -- list
```

Адрес локальной базы лежит в `server/.env` (файл не коммитится): `DATABASE_URL`
для макросов `sqlx`, `APP_DATABASE_URL` для сервера и для этого CLI. Из каталога
`server/` он подхватывается сам; из корня репозитория - нет (§3.1).

**Интеграционные тесты `api`.** Харнесс не может выдать себе личность: он создаёт
запись через `db::users::create`, как это делает CLI, и входит через настоящий
`POST /api/auth/login`. Отсюда `support::Harness`, который носит пул рядом с
роутером:

```rust
let router = support::router(pool);
let session = router.sign_in(json!({
    "username": "dean-01", "role": "dean", "scope_faculty_code": "FAC03",
})).await;
let reply = send(&router, authenticated(&session, "GET", "/api/internal/ping")).await;
```

`sign_in` аддитивен и идемпотентен - как CLI: повтор для одного логина
переиспользует строку и добавляет грант, если его нет. Он никогда не отзывает,
поэтому тесту с другой ролью нужен другой логин.

**e2e.** Учётные записи должны существовать **до** прогона; их создаёт
`bun fixtures/seed.ts` через `cargo run --bin manage-users`. Побочный эффект
этого устройства - CLI покрыт e2e-прогоном.

**Изменение поверхности.** Маршруты и DTO живут в
`server/crates/api/src/routes/auth.rs`; после правки перегенерируйте контракт и
клиент (`vp run gen:api`) и закоммитьте их вместе с изменением Rust - дерево
никогда не должно содержать устаревший контракт (AGENTS.md инвариант #5).
