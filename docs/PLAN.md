### 1.2. Измерение «факультет» существует только начиная с 2025/26 учебного года

До 2025/26 все проверки выполнялись 16–20 центральными операторскими учётными записями, поэтому атрибуция тех лет по факультетам **невосстановима** из этой выгрузки ни с какой степенью уверенности. С 2025/26 в данных 172 различных проверяющих (что совпадает с «Активные пользователи: 172»), поэтому сопоставление e-mail → кафедра становится осмысленным.

Следствие для ТЗ §4.2 §4 (разбивка по факультетам/кафедрам) и для фильтра по факультету: реальные разбивки для 2025/26 учебного года и далее, единая корзина «Не распределено» для более ранних лет - если офис регистратора не предоставит историческое сопоставление (D2). Это должно быть указано на самой странице, а не скрыто: сноска «Разбивка по подразделениям доступна с 2025/26 уч. года».

### 1.3. Граница персональных данных для производных ключей

`work_ref` и `reviewer_ref` - это дайджесты HMAC-SHA256, вычисляемые внутри парсера приёма данных с серверным pepper (`APP_INGEST_PEPPER` - только переменная окружения, никогда в базе данных, никогда в Git); открытые название, авторы, имя проверяющего и e-mail отбрасываются в той же функции и никогда не попадают в логи. `staff_units` хранит дайджест плюс **маскированную метку** (`z***v.vn@teachers.tou.edu.kz`), чтобы администратор мог поддерживать сопоставление, а хранилище при этом не содержало справочника сотрудников.

Это расширяет инвариант №1 (никаких персональных данных), а не ослабляет его - ничего именного или обратимого не сохраняется, - но это его интерпретация, поэтому до реализации требуется явное решение человека (**D3**) и ADR-008.

### 1.4. Измеренные риски качества данных (все должны обрабатываться импортёром)

- Поля в кавычках, содержащие `;` и встроенные переводы строк: до 117 строк в год. Используйте крейт `csv`; наивное разбиение по разделителю неверно.
- Строки со сдвигом колонок: 4 строки в 2024/25 содержат URL отчёта в колонке «Статус» → строгая построчная валидация, отклонение в `ingest_batches.errors`, отображение в админском интерфейсе. Никогда не угадывать.
- Дублирующиеся ссылки на отчёты в более ранних годах (4 926 уникальных из 5 022 в 2021/22) → группировка попыток плюс идемпотентный upsert.
- Документы со статусом «Удален»: 272 из 5 429 в 2024/25 → включать или исключать из аналитики (D6).
- UTF-8 **с BOM**, разделитель `;`, десятичная запятая, русский формат даты.

### Фаза 1 - Хранилище, приём данных, комплаенс (02.09 – 08.09 · Этап 1 по ТЗ)

Гейт: e2e внутри хостового iframe с проверкой сообщений о высоте и отсутствия любых элементов навигации.

**W2.6 - Локализация RU/KK/EN** · 1.5 дн. · поток: app
Настоящие переводы на русский и казахский для каждой строки (никаких английских заглушек), английский как опциональная третья локаль; форматирование чисел и дат через `Intl` для каждой локали; cookie локали плюс переопределение `?lang`; покрытие казахских глифов проверено в выбранном шрифте.
Гейт: ошибка сборки при нарушении паритета ключей; e2e переключает RU↔KK и проверяет переведённые заголовки разделов.

**W2.7 - Гейты доступности и производительности** · 1 дн. · поток: fixtures/e2e
Playwright с `@axe-core/playwright`, сканирующий публичный маршрут и маршрут встраивания; LCP измеряется на профиле с ограничением сети; проверки контраста на токенах графиков.
Гейт: ноль нарушений axe с влиянием ≥ serious; LCP в пределах бюджета D9.

### Фаза 3 - Внутренний контур (15.09 – 22.09 · Этап 3 по ТЗ)

**W3.1 - SSO / OIDC** · 2 дн. · поток: api
`/api/auth/{login,callback,logout,me}` с PKCE и state, сессии в базе данных, cookie `HttpOnly`/`Secure`/`SameSite=Lax`, сопоставление групп AD → `role_kind` и области видимости, режим аутентификации `dev` для тестов и путь запроса доступа для аутентифицированных пользователей без роли.
Гейт: интеграционные тесты полного code flow против мок-IdP; тесты на фиксацию сессии и CSRF.

**W3.2 - Матрица RBAC** · 1 дн. · поток: api
Каждая роль × каждый внутренний/админский эндпоинт × комбинация «в области видимости / вне области» проверяется в одном табличном тесте. Это свидетельство приёмки для ТЗ §10.5.
Гейт: тест матрицы падает, если новый эндпоинт добавлен без строки (управляется реестром).

**W3.3 - Внутренние эндпоинты** · 2 дн. · поток: api + db
Публичные формы плюс фильтры `faculty`/`department`/`program`, плюс `/departments-matrix`, `/rechecks`, `/escalations`, `/usage`; фильтрация по области видимости только в SQL; подавление по-прежнему применяется к агрегированным представлениям, предназначенным для широкой аудитории.
Гейт: тесты области видимости на уровне запросов и тесты эндпоинтов; показатель улучшения при повторной проверке сравнивается с фикстурой полного перебора.

**W3.4 - Журнал аудита** · 1 дн. · поток: api
`AuditLayer` на каждом внутреннем и админском ответе 2xx, включая выгрузки; `/api/admin/audit` с пагинацией и фильтрацией; хранение ≥ 1 года задокументировано, задачи удаления нет.
Гейт: тест, проверяющий одну строку аудита на просмотр раздела и на выгрузку с нормализованными фильтрами; тест обеспечения режима «только добавление» (уже на уровне схемы).

**W3.5 - Выгрузка PDF/XLSX** · 2.5 дн. · поток: reports
`POST /api/{public,internal}/export?format=pdf|xlsx` с переиспользованием DTO, прошедших скрининг; XLSX через `rust_xlsxwriter`; PDF через Typst с брендированным шаблоном (логотип, `#1D3D66`/`#DE6E35`, RU/KK, покрытие кириллических и казахских глифов); водяной знак «Для служебного пользования» на внутренних выгрузках; действие аудита `export_*`.
Гейт: snapshot-тесты на оба формата; страж на регулярном выражении, утверждающий отсутствие строк, похожих на ФИО, и отсутствие числовых значений в подавленных ячейках; e2e-скачивание с разбором.

**W3.6 - Внутренний интерфейс** · 2.5 дн. · поток: app
Страницы `/app/*` для разделов 2, 3, 4 (детализация факультет→кафедра через TanStack Table; уровень ОП заблокирован на D2), 6, 7, 8 и 9; варианты фильтров с учётом области видимости; кнопки выгрузки, подключённые к W3.5; TanStack Virtual для длинных журналов (аудит, пакеты - матрица подразделений ограничена по размеру и остаётся невиртуализированной).
Гейт: e2e по каждой роли - декан видит только свой факультет и в интерфейсе, **и** в сетевых ответах.

**W3.7 - Админский интерфейс** · 2.5 дн. · поток: app
Источники и расписания с ручным запуском; пакеты приёма данных с построчными ошибками; редакторы справочников, алиасов, `staff_units` (маскированные метки), `work_type_rules` и `initiator_rules`; роли и области видимости; настройки (k, порог оригинальности, корзины, квартал снимка, политика по удалённым документам); браузер аудита. Формы через TanStack Form + Valibot.
Гейт: e2e для админских сценариев; изменение `k` в настройках заметно меняет подавление на публичной странице в пределах TTL.

### Фаза 4 - Отчёты, нагрузка, приёмка (22.09 – 30.09 · Этап 4 по ТЗ)

**W4.1 - Годовой отчёт по Приложению 1** · 2.5 дн. · поток: reports
Семь таблиц, воспроизводящих форму (общие показатели; по типам работ; распределение по диапазонам; по факультетам; повторные проверки; эскалации; использование системы); PDF и XLSX; неизменяемые снимки (путь записи «только один раз» плюс хеш содержимого в `report_snapshots`); флаг `published` выводит файл на публичный контур.
Гейт: snapshot-тест, сравнивающий каждую таблицу с агрегатами фикстур, вычисленными полным перебором; тест неизменяемости (перегенерация создаёт новый снимок, никогда не перезаписывает).

**W4.2 - Планирование** · 0.5 дн. · поток: reports/ingest
Годовая генерация 1 сентября за завершившийся учебный год (под рекомендательной блокировкой, ADR-005) плюс ручная генерация за произвольный период.
Гейт: модульный тест планировщика с внедрённым источником времени.

**W4.3 - Отчёты по реальным данным за 2024/25 и 2025/26 учебные годы (ТЗ §10.9)** · 1 дн. · поток: orchestrator
Локальный приём `stats/` через настоящий конвейер (который и выполняет анонимизацию), генерация обоих годовых отчётов, передача в Комплаенс. Процедура задокументирована в `deploy/RUNBOOK.md`; результаты никогда не коммитятся.

**W4.4 - Нагрузка и производительность** · 1.5 дн. · поток: fixtures/e2e
Скрипты k6 против стенда, засеянного 250 k строк: `/api/public/summary` p95 < 300 мс, LCP дашборда в пределах бюджета D9; длительность обновления матпредставлений измерена и зафиксирована; ночная задача CI.
Гейт: бюджеты обеспечиваются падением CI, а не отчётами.

**W4.5 - Наблюдаемость и эксплуатация** · 1 дн. · поток: api/ops
`/metrics` (длительности запросов, счётчики приёма данных, счётчики подавлений, отказы записи аудита); JSON-логи `tracing` без субъекта и e-mail на публичных путях; `/readyz` в состоянии degraded, когда самый свежий пакет старше 26 ч; ночной `pg_dump` плюс архивирование WAL с отрепетированным учебным восстановлением, описанным в руководстве по эксплуатации (runbook).
Гейт: smoke-тест, проверяющий существование имён метрик; учебное восстановление, выполненное один раз против staging и датированное в руководстве.

**W4.6 - Развёртывание** · 1 дн. · поток: ops
Многостадийный Dockerfile, который также собирает фронтенд и раздаёт его из бинарника (текущий собирает только бэкенд); compose для staging; заметки по обратному прокси, TLS и CSP; матрица переменных окружения; обращение с секретами `APP_INGEST_PEPPER` и учётными данными OIDC.
Гейт: `docker compose up` из чистого чекаута даёт работающий публичный дашборд на фикстурах.

**W4.7 - Пакет приёмки** · 1 дн. · поток: orchestrator
`docs/ACCEPTANCE.md`, сопоставляющий ТЗ §10.1–§10.9 с точной командой, доказывающей каждый пункт; разбор с Комплаенс; список дефектов; УПД.
Гейт: у каждого пункта §10 есть зелёная команда либо письменно зафиксированное и подписанное отклонение.

**Критический путь:** ответ по D2 → фикстуры W0.3 → W1.1 → W1.4 → W1.5 → W2.1 → W2.4 → W3.3 → W4.1 → W4.7 (W1.0 идёт параллельно; команда системы-источника вовлечена только в ревью его контракта).

Всё, что находится ниже приёма данных по потоку, зависит от решений по правилам вывода для исторической загрузки - именно поэтому ответы по D2, D3 и D6 нужны в первые три дня. W3.1 (SSO) имеет внешний срок ожидания и является вторым по вероятности источником сдвига сроков; режим аутентификации `dev` позволяет фазе 3 двигаться, пока регистрация в ожидании, но для приёмки §10.5 нужен настоящий IdP.

Итого ≈ 45 агенто-дней примерно в 7 параллельных потоках за 4.5 календарной недели - выполнимо; решение по D1 сняло крупнейшую внешнюю неизвестность, а D2 (данные офиса регистратора) стала самой напряжённой внешней зависимостью.

| R10 | У KPI охвата и средней длительности проверки нет источника данных                                                     | Низкое  | Скрываются при отсутствии данных, согласно ТЗ «при наличии данных»; пути ручного ввода существуют                                                                                                                                         |

## 7. Базовые правила исполнения

- Один вертикальный слайс на коммит; генерируемые артефакты (`contracts/openapi.json`, `apps/web/src/api/`, `.sqlx/`) коммитятся вместе с исходным изменением, которое их вызвало.
- Ни один гейт не ослабляется, не пропускается и не помечается `#[ignore]` (инвариант №7 в AGENTS.md). Красный гейт - это ошибка в изменении, а не в гейте.
- Каждая новая зависимость, таблица, группа эндпоинтов или правило вывода получает ADR в том же изменении (001–016 приняты; следующий свободный номер: **017**).
- Всё, что затрагивает инварианты в сторону ослабления, а также D1–D11, останавливается и спрашивает человека.
