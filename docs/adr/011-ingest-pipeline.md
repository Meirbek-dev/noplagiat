# ADR-011 - Конвейер ингеста: модули, размещение SQL и его зависимости

**Статус:** принято · 30.08.2026
**Реализует:** слайс **W1.5** в [PLAN.md](../PLAN.md) §3 (TZ §3.3.1–§3.3.5, §6.1).
**Регулируется:** [ADR-008](008-legacy-derivation-and-hmac.md) (правила вывода для CSV - нормативны) и [ADR-010](010-source-ingest-contract.md) + [`contracts/ingest-source.schema.json`](../../contracts/ingest-source.schema.json) (режим API - нормативны). Этот ADR не добавляет ни одного собственного правила; он фиксирует, **как** те два исполняются, единственное отклонение по лейнам и каждую зависимость, полученную крейтом.

## Контекст

W1.5 превращает заглушку `ingest` в настоящий конвейер. Два режима пишут в одну таблицу фактов:

- **Режим API** - основной путь после запуска собственной системы `noplagiat.tou.edu.kz`. Записи приходят со всеми полями TZ §3.1 и, по контракту, вообще без ПДн.
- **Режим CSV** - однократный исторический бэкфилл легаси-выгрузок вендора за 2021–2026 годы и запасной вариант из TZ §3.3.2. Здесь применяется весь слой вывода из ADR-008.

Всё нижеследующее определяют три ограничения: инвариант, согласно которому ни имя, ни e-mail, ни название не могут попасть в колонку или строку лога (AGENTS.md #1); идемпотентность (TZ §3.3.4); и тот факт, что лейн `db` одновременно строит `crates/db` и миграцию 0003.

## Решение

### 1. Топология модулей

| Модуль       | Ответственность                                                                                                                 |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| `source_csv` | Диалект ADR-008 §1: срезание BOM, `;`, кавычки RFC-4180, контракт заголовка из 14 колонок, `system-usage`                       |
| `row`        | Одна запись → один `ParsedRow` или одна типизированная `RowRejection`. **Единственная область, где существует открытый текст.** |
| `norm`       | `norm(s)` (NFC → обрезка → схлопывание → нижний регистр), разбор «Да», `masked_label`                                           |
| `refs`       | `Pepper` плюс два вывода HMAC (ADR-008 §2)                                                                                      |
| `rules`      | Сопоставление `work_type_rules` / `initiator_rules` / `staff_units`, вместе с заглушками                                        |
| `attempts`   | Лестница из ADR-008 §3 - чистая функция над множеством ключей попыток                                                           |
| `store`      | Все SQL-выражения (см. §2)                                                                                                      |
| `pipeline`   | Оркестрация партии: чтение → вывод → группировка → upsert → обновление представлений                                            |
| `api`        | Вытягивание по ADR-010: трейт `SourceApi`, REST-реализация, курсор, валидация записей                                           |
| `scheduler`  | Ночной тик и раннер на каждый источник (ADR-005)                                                                                |
| `error`      | Все типизированные отказы; ничто здесь не может хранить исходный текст                                                          |

**Граница ПДн - это граница функции.** `row::parse_row` заимствует название, авторов, имя и e-mail проверяющего из `csv::StringRecord`, передаёт их в HMAC и в сопоставители правил и возвращает `ParsedRow`, у которого **нет ни одного поля, способного их хранить**. Ничто ниже по потоку не может утечь тем, до чего не дотягивается. `Debug` у `Pepper` - это `Pepper(<redacted>)`, а `domain::WorkRef`/`ReviewerRef` уже лишены `Serialize` и имеют затёртый `Debug`.

### 2. Отклонение по лейнам: SQL ингеста живёт в `ingest::store`, а не в `db`

AGENTS.md §4 помещает схему и запросы в лейн `db`. Для этого слайса путь записи живёт в `ingest::store`, поскольку оба лейна выполняются одновременно и иначе правили бы одни и те же файлы.

Это уже, чем кажется:

- `store` - **однопишущий транзакционный путь**. Он никогда не обслуживает запрос, поэтому ему не нужен `compliance::Scope` - инвариант #3 управляет _запросными_ функциями, а их здесь нет.
- Каждое выражение идёт через `sqlx::query!`/`query_scalar!` (проверяются на этапе компиляции против живой схемы), ровно как требует AGENTS.md §5.
- Единственное динамическое выражение - `REFRESH MATERIALIZED VIEW [CONCURRENTLY] <name>`, чья цель является идентификатором. Оно собирается из `pg_matviews` - каталога, а не значения запроса - экранируется удвоением `"` и затем пропускается через `sqlx::AssertSqlSafe`. AGENTS.md §5 запрещает конкатенировать _пользовательский ввод_; здесь пользовательского ввода нет.

Когда лейн `db` будет готов его вобрать, `ingest::store` переезжает целиком; ни один вызывающий код за пределами крейта от него не зависит.

### 3. Группировка попыток дедуплицирует по `(checked_at, source_check_id)`, а не по одному идентификатору

ADR-008 §3 нумерует попытки, упорядочивая `(checked_at, source_check_id)` внутри одного `work_ref`. Порядковые номера вычисляются по **объединению** строк, уже находящихся в хранилище для этой работы, и строк текущей партии, поэтому лестница, охватывающая две партии, остаётся непрерывной, а повторный запуск воспроизводит ровно те же пары.

Дедупликация этого объединения по одному лишь `source_check_id` была бы ошибкой: ≈2 % перепроверенных работ в легаси-выгрузке переиспользуют одну ссылку на отчёт между попытками (`fixtures/README.md`), поэтому идентификатор не уникален внутри работы. А пара - уникальна: две попытки одной работы никогда не записываются в одну минуту. Это уточнение правила, а не его изменение: при различающихся ссылках оба варианта совпадают.

**Поздно пришедшая более ранняя попытка перенумеровывает сохранённые строки.** Иначе у работы оказались бы две строки с `attempt_no = 1`, и доля повторных проверок из TZ §4.2 §6 была бы неверной. Поскольку `UNIQUE (source_check_id, attempt_no)` проверяется построчно и не является отложенным, перезапись выполняется в две фазы: сначала затронутые `attempt_no` инвертируются в отрицательные, затем присваиваются окончательные. Статус движется вместе с порядковым номером (попытка > 1 → recheck).

### 4. Строки «Удален» не пропускаются, а сохраняются через upsert

ADR-008 §4 исключает удалённые строки из аналитики; миграция 0003 делает `deleted` **измерением** `agg_monthly`, а не фильтром. Поэтому ингест сохраняет их с `deleted = true` и учитывает в `ingest_batches.rows_skipped_deleted`, благодаря чему `settings.exclude_deleted` остаётся чистым переключателем на этапе запроса, а не поводом для повторного ингеста.

Одно исключение, продиктованное ADR-008 §1: удалённая строка, чья ссылка на отчёт не разбирается, не имеет идентификатора и не может стать фактом. Она учитывается в `rows_skipped_deleted` и отбрасывается, никогда не угадывается и никогда не засчитывается как отбраковка (что привело бы к её двойному учёту относительно сайдкара фикстур).

### 5. Журналирование партии находится вне транзакции данных

Строка `ingest_batches` открывается до транзакции и закрывается после неё. Поэтому отказ всё равно оставляет строку со `status = 'failed'` и списком её ошибок - партия, исчезнувшая вместе с собственной записью об отказе, неотличима от партии, которая никогда не запускалась (TZ §3.3.5).

Транзакция данных берёт `pg_advisory_xact_lock(0x6e706c6700000001)` - одну фиксированную проектную константу, используемую каждым раннером (ночная задача, CLI и административный триггер, который лейн `api` добавляет в W3.7), поэтому запуск является единственным в полёте между процессами. Блокировка уровня транзакции освобождается и при коммите, _и_ при падении, поэтому мёртвый раннер никогда не заклинивает расписание.

Материализованные представления обновляются **после** коммита - `REFRESH … CONCURRENTLY` не может выполняться внутри блока транзакции. Набор представлений перечисляется из `pg_matviews`, а не задан жёстко, поэтому два представления, добавленные миграцией 0003, обновляются без изменений в ингесте; представление, которое не заполнено или не имеет уникального индекса, откатывается к блокирующему обновлению.

### 6. Числа никогда не путешествуют как числа с плавающей точкой

Проценты передаются как целые сотые от CSV-парсера до SQL-выражения, где `t.originality::numeric / 100` даёт значение `NUMERIC(5,2)`. Ни одно число с плавающей точкой не решает, в какую корзину гистограммы попадёт проверка, а парсер отвергает третий знак после запятой вместо того, чтобы округлить его прочь. Колонки-перечисления передаются как `text` и приводятся в SQL (`t.status::check_status`), что позволяет сохранить всё выражение проверяемым на этапе компиляции без пользовательского маппинга типов.

### 7. Семантика правил

- `work_type_rules.pattern` - сопоставление **подстроки** без учёта регистра с `norm(title)`, первое совпадение по `(priority, id)` (ADR-008 §7). Именно это реализует `fixtures/expected.ts`, поэтому они не могут разойтись.
- `initiator_rules.pattern` - **регулярное выражение** над `norm(email)`. Значения по умолчанию из ADR-008 §5 смешивают привязанную к началу форму (`^registrar`, `^reg\.`) с непривязанной (`@teachers.tou.edu.kz`); администратору, редактирующему таблицу, нужна одна предсказуемая семантика для обеих. Шаблон, который не компилируется, пропускается с предупреждением, называющим id правила, - одна неудачная правка администратора не должна останавливать ночной ингест.
- `staff_units` - ключом служит HMAC проверяющего; непривязанные проверяющие получают заглушки `UNASSIGNED` и для факультета, _и_ для кафедры.
- `dict_aliases` - консультируются в режиме API, когда код источника не является `code` из словаря. Режим CSV вообще не несёт меток подразделений или типов работ (PLAN §1.1), поэтому его таблицы правил ссылаются прямо на id словарей.

### 8. Режим API

`SourceApi` - это трейт с асинхронным методом, возвращающим `impl Future + Send` (без `dyn`, без `async_trait`): планировщик знает, что использует `RestSourceApi`, а тесты знают, что используют реализацию в памяти. `SourceRecord` помечен `#[serde(deny_unknown_fields)]` - это Rust-зеркало `additionalProperties: false` из схемы, которое составляет _всю_ гарантию анонимизации (ADR-010 §4) и не может быть ослаблено. Курсор продвигается только после фиксации строк страницы. `work_ref`/`reviewer_ref` остаются NULL; пеппер не нужен.

Учебный год берётся из момента времени записи в фиксированном университетском смещении +05:00 независимо от того, с каким смещением она была сериализована, поэтому календарное правило ADR-008 §8 означает одно и то же в обоих режимах.

### 9. CLI и расписание

`server/src/bin/ingest_csv.rs` реализует интерфейс ADR-008 §10 дословно (`--dir`, `--documents`, `--source`, по умолчанию `csv-backfill`; `APP_DATABASE_URL` + `APP_INGEST_PEPPER`), печатает таблицу «прочитано/сохранено/отбраковано/удалено» по годам и завершается с ненулевым кодом при любом отказе партии - `fixtures/seed.ts` уже вызывает его именно так. Пеппер читается _до_ подключения к базе данных: наполовину загруженный год с непригодными референсами хуже, чем отсутствие запуска.

`server/src/main.rs` порождает `ingest::spawn_scheduler` (ADR-005). Тик - в 02:00 при +05:00, вычисляется по местным гражданским часам. `SchedulerConfig::from_env` терпимо относится к отсутствию пеппера или токена источника - на хосте, работающем только с API-источниками, пеппера нет, - а запуск конкретного источника падает громко.

## Зависимости, добавленные в `crates/ingest`

| Крейт                   | Зачем                                                                                                                                                             |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hmac` 0.13             | ADR-008 §2 требует HMAC-SHA256. RustCrypto, уже присутствует в графе lock-файла через SCRAM-аутентификацию `sqlx`                                                 |
| `sha2` 0.11             | Хеш, лежащий в его основе; тот же граф                                                                                                                            |
| `unicode-normalization` | `norm(s)` начинается с Unicode NFC, а в `str` из std нет NFC. На нём же держатся группировка и классификация типов работ                                          |
| `regex` 1.13            | Шаблоны `initiator_rules` (§7). Линейность по построению, поэтому шаблон, заданный администратором, не может стать отказом в обслуживании                         |
| `sqlx` 0.9              | Отклонение по лейнам из §2 помещает путь записи сюда; те же фичи, что у `db`, плюс `time`                                                                         |
| `time` 0.3              | Привязка `TIMESTAMPTZ`. Уже подтягивается фичей `sqlx`, которую включает `db`; точна, в отличие от кругового преобразования секунд эпохи через `double precision` |
| `jiff` 0.2              | Арифметика моментов и гражданского времени, на которой уже говорит `domain` (чтение +05:00, вывод учебного года, ночной тик)                                      |
| `serde_json`            | `ingest_batches.errors`, `ingest_sources.cursor`, `settings` и формат обмена по ADR-010                                                                           |
| `serde` (derive)        | Типы записи и курсора по ADR-010                                                                                                                                  |
| `reqwest` `query`       | Не новая зависимость - существующий `reqwest` получил фичу `query` ради параметров курсора из ADR-010                                                             |
| `tracing-subscriber`    | **Только dev-зависимость.** Приёмочный тест TZ §6.1 захватывает каждую выдаваемую строку лога и сканирует её на предмет структур, похожих на имена                |

`csv`, `db`, `domain`, `thiserror`, `tokio` и `tracing` были объявлены ранее. `server` не получил ни одной зависимости: бинарник `ingest-csv` переиспользует `anyhow`, `dotenvy`, `db`, `tokio` и `tracing-subscriber`.

## Последствия

- `ingest::store` - временное пристанище. Перенос его в `db` в будущем не изменит ни одного вызывающего кода за пределами крейта.
- Ночное расписание, CLI и будущий административный триггер берут одну и ту же advisory-блокировку, поэтому добавление второй реплики сервера не потребует изменений (изначальное утверждение ADR-005, теперь действительно проверенное).
- Режим API полностью протестирован до появления эндпоинта источника: реализации `SourceApi` в памяти скармливаются страницы, проверенные на соответствие ограничениям схемы, поэтому расхождение с реальным источником окажется диффом схемы (снижает риск PLAN R1a).
- Доказательство по TZ §6.1 - это один именованный тест, который загружает намеренно похожие на имена данные и затем сканирует **каждую** колонку типов `text`/`varchar`/`char`/`json`/`jsonb` каждой таблицы плюс каждую захваченную строку лога. Это приёмочный артефакт, а не код-ревью.
- Сайдкар фикстур (`fixtures/out/<ay>/malformed.json`) превращает golden-тест в равенство: прочитано / сохранено / отбраковано / удалено проверяются по точным числам, а также проверяются _индексы_ отбракованных записей.
