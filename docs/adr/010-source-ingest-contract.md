# ADR-010 - Контракт ингеста для новой системы `noplagiat.tou.edu.kz`

**Статус:** принято · 30.08.2026
**Закрывает:** слайс **W1.0** в [PLAN.md](../PLAN.md) §3; следствие **D1** (исходная система пишется с нуля силами университета).
**Схема:** [`contracts/ingest-source.schema.json`](../../contracts/ingest-source.schema.json) (JSON Schema draft 2020-12) - нормативна для формата обмена.
**Замечание о нумерации:** номер 009 занят топологией деплоя SSR; данный ADR имеет номер 010.

## Контекст

Поскольку исходная система строится внутри университета, а не обнаруживается снаружи, её API ингеста **проектируется**, а не реконструируется обратной разработкой. Это убирает с основного пути данных весь слой вывода из [PLAN §1](../PLAN.md#1-the-data-reality-gap--read-this-before-anything-else) - тип работы, подразделение, номер попытки, статус, эскалацию, роль инициатора. Правила [ADR-008](008-legacy-derivation-and-hmac.md) остаются в силе, но только для однократного исторического бэкфилла выгрузок вендора за 2021–2026 годы и как CSV-запасной вариант из TZ §3.3.2.

Дизайн определяют два ограничения:

1. **Анонимизация должна выполняться на стороне источника, по контракту.** Инвариант #1 дашборда («никаких ПДн, никогда») сегодня защищается парсером ингеста. Если источник может просто не присылать имена, e-mail, названия и текст документов, инвариант становится свойством формата обмена - проверяемым схемой, в обе стороны, ещё до сохранения хотя бы одной строки.
2. **Ингест должен быть возобновляемым и идемпотентным** (TZ §3.3.4). Дашборд тянет данные; источник их не проталкивает. Упавший запуск обязан возобновиться ровно с того места, где остановился, а повторный запуск той же страницы ничего не должен изменить.

## Решение

### 1. Версионированный эндпоинт вытягивания

```
GET {base_url}/api/analytics/v1/checks?limit=&checked_at=&check_id=
```

- Мажорная версия находится в пути. Ломающее изменение - это новый путь, а не переопределение `v1`; таким образом `ingest_sources.base_url` закрепляет одну версию контракта на каждый настроенный источник.
- Аутентификация - bearer-токен сервиса (`Authorization: Bearer …`), хранящийся в `APP_SOURCE_TOKEN`; никогда в базе данных, никогда в Git, никогда в логах. Он даёт доступ на чтение только этого эндпоинта.
- Ответ - одна страница JSON-объекта, описанного схемой: `{"records": [...], "next_cursor": {…} | null}`.
- `limit` носит рекомендательный характер; сервер вправе вернуть меньше записей. `next_cursor: null` означает «вызывающая сторона догнала источник» и является единственным сигналом конца потока.

### 2. Курсор по паре `(checked_at, check_id)`

Записи упорядочены по `(checked_at ASC, check_id ASC)`, и курсором служит та же пара, исключительно: следующая страница начинается строго после неё. Именно составной ключ делает вытягивание детерминированным, когда множество проверок разделяют одну временную метку - курсор по одному лишь `checked_at` либо теряет строки, либо повторяет их на границах секунд, а легаси-выгрузки показывают до сотен проверок в минуту.

Курсор хранится дословно в `ingest_sources.cursor` (JSONB) и продвигается только после фиксации строк страницы, поэтому падение приводит к повторному чтению не более одной страницы. В сочетании с upsert по `ON CONFLICT (source_check_id, attempt_no)` повторное чтение страницы не имеет эффекта.

Запись, чей `checked_at` впоследствии **исправлен** источником, должна быть переслана с исходным `check_id`; upsert её заменит. Исправления, сдвигающие запись _за_ курсор, - единственный случай, который инкрементальное вытягивание увидеть не может, поэтому источник дополнительно предоставляет тот же эндпоинт для произвольного окна (`checked_at`, установленный в любой прошлый момент) ради периодической полной пересинхронизации.

### 3. Каждое поле TZ §3.1 - нативно

Одна запись несёт, без какого-либо вывода на нашей стороне:

| Поле                                                               | Контракт                                                                                              |
| ------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| `check_id`                                                         | непрозрачный, стабильный, ≤ 256 символов; становится `checks.source_check_id`                         |
| `checked_at`                                                       | RFC 3339 со смещением                                                                                 |
| `attempt_no`                                                       | ≥ 1, назначается источником (он знает, какие подачи относятся к одной работе)                         |
| `work_type_code`                                                   | код словаря, разрешается через `dict_aliases`; `other`, если не классифицирован                       |
| `faculty_code`, `department_code`                                  | коды словарей; `UNASSIGNED`, если источник не может привязать проверку                                |
| `program_code`                                                     | допускает NULL - детализация по ОП условна (D2)                                                       |
| `originality_pct`                                                  | 0–100, два знака после запятой                                                                        |
| `self_citation_pct`, `citation_pct`, `match_pct`, `ai_content_pct` | 0–100, допускают NULL; сохраняются, но пока не отображаются (PLAN §1.1)                               |
| `status`                                                           | `accepted` \| `needs_revision` \| `rejected` \| `recheck` - собственный вердикт источника             |
| `escalated`                                                        | булево, независимо от `status` (ADR-008 §4)                                                           |
| `suspicious`, `suspicion_cleared`                                  | булевы; входные данные, стоящие за `escalated`, сохраняются ради аудируемости                         |
| `initiator`                                                        | `student` \| `staff_self` \| `registrar` \| `other`                                                   |
| `duration_seconds`                                                 | целое неотрицательное, допускает NULL - единственный источник среднего времени проверки из TZ §4.2 §8 |
| `deleted`                                                          | булево; исключается из фактов согласно `settings.exclude_deleted`, учитывается в партии               |

`status` принимается как авторитетный. `settings.status_rules` по-прежнему существует и по-прежнему управляет CSV-путём, и его можно применить и к строкам из API, когда Комплаенс оспорит вердикты источника (R5) - это изменение настроек, а не схемы.

### 4. Полное отсутствие полей с ПДн

Схема задаёт `"additionalProperties": false` для объекта записи, а список свойств не содержит ни имени, ни e-mail, ни названия, ни автора, ни текста, ни поля со ссылкой на отчёт. Последствия:

- Источник, который начнёт присылать `"author"`, громко провалит валидацию вместо того, чтобы тихо заполнить колонку.
- В режиме API ингесту не нужны ни пеппер, ни HMAC: `work_ref`/`reviewer_ref` остаются NULL, потому что `attempt_no` и подразделение приходят напрямую. `APP_INGEST_PEPPER` остаётся обязательным только для режима CSV.
- Привязка к подразделению на стороне источника означает, что сопоставление «проверяющий → кафедра» живёт там, где уже находится справочник сотрудников, а не восстанавливается здесь из `staff_units`.

Схема - двусторонний артефакт: команда источника реализует её, `ingest` по ней валидирует, и тот же файл порождает тестовые фикстуры для режима API - так что «фикстура расходится с источником» становится диффом схемы, а не сеансом отладки.

## Последствия

- Режим API тестируем ещё до появления эндпоинта источника: фикстуры генерируются из схемы, и на них выполняются golden-тесты W1.5 (снижает риск R1a).
- `ingest_sources` содержит по одной строке на каждый настроенный источник (`kind = 'api'`, `base_url`, `schedule`, `cursor`), поэтому переключение с бэкфилла на живое вытягивание - административное действие, а не деплой.
- Дашборд не может обнаружить сбой анонимизации на стороне источника иначе как через закрытое множество свойств схемы - в этом и состоит вся гарантия, поэтому `additionalProperties: false` ослаблять нельзя.
- Коды словарей должны быть согласованы с офисом регистратора до того, как источник сможет их выдавать (D2). До тех пор источник выдаёт `UNASSIGNED`/`other`, которые строки-заглушки из миграции 0002 уже принимают.

**Зависимости:** новых нет. Схема валидируется в `ingest` JSON Schema-валидатором, выбранным этим лейном; `domain` и `compliance` не получили новых зависимостей для W1.0–W1.3.
